# Reduct cloud integration — Improvement Kata and implementation plan

## Direction and target

Users enter a Reduct key at Settings → Kask → Data Services and explicitly invoke Reduct cloud media/audio/transcript tools in the Media panel alongside local `educt_*`. Success requires documented request/response contracts, visible provider errors, no secret disclosure or silent local fallback, independent local educt regressions, and an authorized provider-side media/reel outcome. **Proposed engineering horizon:** one to three weeks after expanded endpoint schemas and safe test-media authorization are available, not an operator deadline.

## Current condition and evidence

- At intake, `tasks/reduct-video-analysis-scaffold.md` proposed cloud integration but none was implemented. Local educt is a separate working transcript/EDL system. Data Services already had the OS-keychain write/delete and MCP refresh pattern, so Reduct was added there without a second secret store or enable toggle. Media alone receives `REDUCT_API_KEY`. The panel's generated tool advertisement groups `reduct_*` separately from `educt_*`.
- The operator entered the key in Settings and restarted. Runtime `reduct_connection_status` reported configured; `reduct_connection_probe` performed a live `GET https://app.reduct.video/api/v3/project` using X-Auth-Key with HTTP 200. `reduct_projects_snapshot` returned a bounded ID/title subset. No key was printed or committed.
- The operator pasted authenticated Reduct v3 documentation content on 2026-09-23. It pins the X-Auth-Key header, `https://app.reduct.video/api/v3/` root, ID-keyed GET schema, transcript options, error classifications, exact GET status/transcript paths, POST recording create + raw media-upload + URL media-import examples and response keys. Previously the docs URL redirected to login (HTTP 302) when sent an API key; that does **not** invalidate the text now provided by the operator.
- Using the stored key in explicitly opted-in **read-only** tests, `GET /project/{id}` returned an object keyed by the project ID with a `recordings` ID-keyed map. A selected recording's `GET .../status` and `GET .../transcript.json` both succeeded. A subsequent operator rebuild/restart first exposed eleven Reduct tools; on 2026-09-23 a fresh `list_mcp_tools(filter="reduct_")` returned twelve, including `reduct_reel_detail`. This verifies runtime tool advertisement, not an editor restart in this session or a new live Reel request. A separate running `reduct_connection_probe` returned HTTP 200 for the project-read endpoint without returning private data; it does not verify Reel writes.
- The excerpt's endpoint category lists were blank when pasted. It describes reel `doc-range` and `title` blocks, highlights and redactions in prose, but not their complete JSON fields, response keys, overwrite/mutation preconditions, or reel publication schemas. Reduct warns that DELETE is irreversible, POST can overwrite supplied fields and API audio redaction does not redact transcript text. Do not implement those writes from guessed payloads.

## Acceptance criteria / remaining obstacles

1. **Credential and read-only paths — implemented, verified.** OS-keychain → media-only MCP delivery; project, recording and reel ID/title snapshots, recording status, JSON/TXT transcripts, provider-native highlights read, and reel detail with share-token removal. Provider responses are bounded; errors are typed; pagination is reported unknown. Live provider checks observed project, recording status, JSON/TXT transcripts, highlight GET (ID-keyed map; sampled recording had zero highlights), and an existing reel's ID-keyed title/block response (with 41 blocks in one sample); no content or IDs were printed.
2. **Documented ingest paths — implemented, not live-mutated.** Create a cloud recording (POST JSON title → recording ID), import a public media URL (POST JSON URL → `media_ids`) and upload an indexed gallery audio/video asset (raw POST with URL-encoded filename → `media_id`, 128 MiB cap, stable SHA-256). Results report submission and direct users to recording status rather than claiming transcription complete. A network timeout or unreadable acknowledgement warns that the write *may* have happened. Fixture tests cover paths, acknowledgement shapes, header placement and changed-byte rejection. Next obstacle: safe disposable recording/media and authorization for one live write, plus deployment of the latest MCP/editor artifacts.
3. **Composition/edit — typed first slice implemented, not deployed or live-mutated.** The operator's 55-page Reduct v3 PDF specifies `POST /project/{id}/reel` (page 31), doc-range/title block creation (pages 36–38), and partial block edits (pages 38–39). Four cloud tools now create a Reel, add an ordered clip/title block and edit an existing clip's range; the last checks its `doc-range` type by reading Reel detail before POST. Loopback tests pin bodies, acknowledgements and HTTP 403; an acknowledged submission is not a finished Reel. The OCR report failed quality gates on eleven pages, so relevant fields were verified against the PDF's selectable text. Strikethrough page 41 lists paths **without** write body/response; do not guess. Redaction, publish and media download remain separate scope; before a live POST require an operator-authorized disposable Reduct project/recording and sample media. Next: deployment and authorized end-to-end cloud composition.
4. **Independent local path and deployment — partially verified.** Local educt focused tests passed serially; Reduct tool-surface tests and Media-panel tool advertisement passed on the earlier tool set. Re-run after every new tool count, `./script/clippy`, `cargo check -p zed`, build media MCP and affected widgets, then deploy/restart safely. A running tool-list check confirms advertisement but not execution or an editor restart. On 2026-09-23, 16 focused Reduct fixture tests passed (six opt-in live probes remained ignored), 32 serial local-educt tests passed, and Media source-router tests passed (4/4). The Media-panel suite and `./script/clippy -p hkask-mcp-media -p media_panel` could not compile because `crates/open_ai/src/completion.rs:274` destructures a nonexistent `LanguageModelRequest.max_tokens` field; `cargo check -p zed` also encountered the mismatch at `crates/copilot_chat/src/model.rs:1088`. These are concurrent shared-tree build blockers, not evidence of Reduct failure or success. No release rebuild or editor restart was performed.

## Architecture review and decision (2026-09-23)

**Spec provenance:** the operator's v3 API reference excerpt (X-Auth-Key, ID-keyed JSON, exact read and ingest paths, POST-overwrite/DELETE warnings), the live read-only tests in `tools/reduct.rs`, the media server README, and `kask/docs/reference/mcp-servers/media.md`. The missing expanded reel/block/strikethrough schemas are an evidence gap, not evidence the API cannot do the work.

**Surgical design:** retain `MediaServer` as the single MCP composition root. Its `combined_router` independently registers `educt_router` (local durable transcript/layers/EDL) and `reduct_router` (provider protocol); `MediaServer` holds the only optional Reduct key, supplied from the media-only allowlist. `tools/reduct.rs` already concentrates X-Auth-Key, no-proxy/no-redirect HTTP, typed status/transport errors, bounded reads, ID validation, provider shape parsing, and gallery-identity-verified uploads. The panel advertises names from the generated `TOOL_NAMES`. No upstream-wide provider abstraction, shared local/cloud trait, separate MCP server, or automatic mode router is justified: deleting the Reduct domain module would force provider protocol into each tool, while deleting a proposed generic router would lose no required behavior. Keep the Reduct module as the domain seam; split it only when a new independently useful interface emerges, not because its tests make the file long. The observed project-detail `recordings` and `reels` maps share one bounded, deterministic ID/title projection rather than two copies of the same data leak/error policy. Do not alter local educt or the child-local MediaRouter.

**Pre-mortem (refused lazy version):** copying local EDL fields into an undocumented `doc-range` POST body; equating HTTP 200 on a project GET or fixture green with successful reel mutation; automatically retrying a POST after timeout; silently falling back to educt. Those shortcuts would produce plausible but false success or duplicate/overwrite cloud data.

**Feedback-loop review (pragmatic cybernetics):** sense = typed HTTP outcome and follow-up project/recording/status/highlight/reel-detail GET; decide = distinct missing-key, 400, 403, 404, 429, redirect, 5xx, malformed acknowledgement and uncertain-write error paths; act = explicit cloud POST only. Polarity is balancing (read back before subsequent action), delay is moderate because transcription/import is asynchronous, gain is weak when Reduct supplies no idempotency or immediate completion signal, closure is partial after a timed-out POST, and fidelity is moderate (an acknowledgement ID verifies acceptance, not transcription or Reel render). Never auto-retry ambiguous POST; expose `submitted` and a separate status read. A provider-side idempotency mechanism is unknown, so claiming guaranteed exactly-once mutation would be false. Reduct may follow redirects when it fetches an imported URL; the local DNS check covers only the submitted URL, not provider-side redirects.

**Edge-case interrogation (answered from evidence, not a quiz for the operator):** Does project HTTP 200 prove reel creation? No; only the project-read contract was exercised. Is a `doc-range` block's request schema known from the pasted example? No; the name, start/end and recording ID were described, not the exact JSON field layout/response. Can an indexed media file change between gallery lookup and network send? Yes; upload reads a bounded owned byte buffer and checks its SHA-256 against the indexed asset before sending, while a live POST remains untested. Would deleting the local educt router simplify this? No; it would remove a functioning local capability without increasing Reduct contract knowledge.

**Kata cycle 6 (one measured iteration):** predicted (confidence 0.65) that an explicit highlight GET would return an ID-keyed map and close at least 20% of the declared metacognitive gap (0.85). A live, opt-in GET returned HTTP 200 and `{"highlight":{...}}` structure; the new bounded read tool preserves provider fields and an explicit pagination-unknown marker. The threshold event occurred; Brier `(0.65−1)^2 = 0.1225`. This measures improved knowledge, **not** reel-edit completion. No historical scenario calibration was available and one cycle is insufficient for a stability claim. Next obstacle is a fully specified reel/block write plus safe disposable mutation confirmation. Reel GET fields cannot certify which nested fields are POST-writable (the v3 warning explicitly forbids some nested changes).

## Architecture and risk register

Keep `educt_*` and `reduct_*` separate. No heuristic mode router, no fallback on auth/provider failure, no generic pass-through media service, no duplicate credential setting. The one Reduct HTTP boundary owns X-Auth-Key, no redirects/proxies for that key, status classification, bounded responses, and explicit uncertain-write errors. Media upload accepts only indexed gallery audio/video with unchanged bytes; URL import validates the public source URL before POST. No live mutation has been authorized or claimed. Risk of deploying unverified POST paths: account-side changes or billing; owner for safe sample and operator acceptance is the operator, implementation/test owner is the technical agent. Risk of guessing reel schemas: irreversible overwrite or wrong clip/strikethrough; blocked until documented fields are obtained. No commit is made by this work session; shared-tree commits by other processes must be tracked separately from this report.
