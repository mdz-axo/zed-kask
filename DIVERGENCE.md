# DIVERGENCE.md — zed-kask fork divergence from upstream Zed

> **Purpose:** the headline doc for upstream-sync conflict resolution. Every
> `git fetch upstream && git merge upstream/main` consults this file to know
> which crates/files are divergent and why. Referenced from
> `kask/docs/architecture/zed-host-architecture-plan.md` (§13.4).
>
> **Rule:** everything under `kask/` is ours (additive; upstream never touches
> here → near-zero merge conflict). Everything else tracks upstream; the only
> divergences are the D-seams listed below + the `[workspace.members]` /
> `[workspace.dependencies]` arrays in the root `Cargo.toml`.

## The divergence surface (D1–D32)

Every hKask integration maps to a named, isolated change in zed-kask. These
are the _only_ edits to zed-kask's tree outside `kask/`. Any hKask behavior
that would require touching other Zed crates is a smell — push the logic into
an hKask crate behind one of these seams instead.

Four mechanisms now close that loop (`kask/crates/hkask-mcp/src/runtime.rs`): (1) the keeper task reaps its own connection when the service loop exits on its own, guarded by a generation stamp so a late-exiting keeper cannot remove a healthy replacement installed by a reconnect; (2) `get_peer` filters peers whose `is_transport_closed()` is already true, covering the window before the keeper is scheduled; (3) `start_server_with_env` records a `LaunchSpec` so `call_tool_inner` reconnects on demand and retries **once**, bounded by `RECONNECT_COOLDOWN` (5s) so a crash-looping binary cannot become a process-spawn storm; **(4) a per-server health supervisor** checks transport liveness every 60s (`HEALTH_CHECK_INTERVAL`) and proactively removes dead connections before the next tool call discovers them, with a circuit breaker that stops auto-healing after `MAX_CONSECUTIVE_HEALTH_FAILURES` (3) consecutive failures and logs an operator-actionable error. The supervisor does not call `try_reconnect` directly (the future is not `Send`); it removes the dead connection and relies on mechanism (3) for healing. `start_server_with_env` also retries spawn+handshake up to `STARTUP_MAX_RETRIES` (3) with exponential backoff (500ms→10s) before reporting failure, and pipes child stderr to `tracing` with `target: "hkask.mcp.child"` and the `server_id` field for attributed diagnostics. A TOCTOU race between concurrent `start_server_with_env` calls (e.g. startup + on-demand reconnect) is handled by checking at insert time: the loser's keeper is cancelled and its child process killed, the winner's connection is kept. `stop_server`/`shutdown_all` drop the launch spec and clear `health_failures` so a deliberate stop is not resurrected. The idempotency check is now liveness-based, not presence-based. **Retry safety is classified by provable delivery, not by "was it a transport error".** `ToolPortError` gained two variants: `Unavailable` (no live peer accepted the request — the tool provably did not run, so a retry cannot double a side effect) and `Interrupted` (a live peer accepted it and the connection then failed — **the outcome is unknown**). The distinction is forced by rmcp, which reports both a failed send (`service.rs:921`) and a dropped response channel (`service.rs:555,566`) as the same `ServiceError::TransportClosed`: once a request reaches a live peer, a transport loss is not proof of non-delivery. `is_retryable()` is true for `Unavailable` only; `Interrupted` is never auto-retried, at any layer, because doing so would duplicate state-changing effects (two `kanban_task_create`s, a `swarm_hire` charging credits twice). Internally `DispatchError::{NotDelivered, Interrupted, Failed}` carries this, and only `NotDelivered` drives the one-shot reconnect-and-retry. Pinned by `runtime.rs::reconnect_path_tests::{failed_start_still_records_a_launch_spec_for_later_reconnect, stop_server_clears_the_reconnect_path, shutdown_all_clears_every_reconnect_path, reconnect_is_rate_limited_by_the_cooldown, metadata_only_server_cannot_be_reconnected}` (inline module — these assert on the private `launch_specs` map and `try_reconnect`). **Healing is verified against real child processes** by `tests/reconnect_integration.rs` (5 tests, `--features test-fixture`), which SIGKILLs a controllable fixture MCP server (`src/bin/mcp_test_fixture.rs`) and asserts the next call reconnects and is served by a *new* pid. Each of the first three mechanisms is independently pinned — verified by mutation: disabling reconnect-on-demand fails `killed_server_is_reconnected_on_the_next_call`, and disabling reap+liveness fails `dead_connection_is_reaped_from_the_runtime`. The fourth mechanism (health supervisor) and the startup retry/stderr capture are not yet independently pinned by mutation tests — a follow-up should add a test that kills a server, waits >`HEALTH_CHECK_INTERVAL`, and asserts the supervisor removed the connection without a tool call. The fixture's kill path uses `libc::kill` and **asserts** success, because an earlier version that swallowed the result with `let _ =` made the whole suite pass vacuously with all healing disabled. **Server-side replay protection resolves the `Interrupted` ambiguity for the three tools that cannot absorb a duplicate.** `Interrupted` is unavoidable at the client, so it can only be *resolved* at the server: `hkask-mcp-kata-kanban/src/idempotency.rs` stores `(tool, key) → first response` in the kanban database, and `kanban_task_create` / `kanban_board_create` / `kanban_task_spawn` accept an optional `idempotency_key` and return the original response (plus `replayed: true`) instead of re-running. The claim is a single `INSERT OR IGNORE` whose zero-rowcount *is* the already-seen signal, so two concurrent replays cannot both win — no read-then-write race, and no transaction (`dyn DatabaseDriver` exposes none). Reservation is two-phase (`reserve` → work → `record`) because the work happens between: a key claimed but never recorded is `Pending`, reported as unknown rather than silently re-run, since whether it landed is precisely what is unknown; a cleanly-failed call calls `release` so a retry starts fresh instead of inheriting that verdict. Only these three needed it — `task_update`/`task_assign`/`task_delete`/`board_delete` already converge, and `swarm_clone_to_local`/`swarm_push_to_cloud`/`swarm_create_local_agent` are keyed by `agent_name`. **`swarm_hire` was already protected** by `spend_gate`'s consume→spend→refund over a single-use `ConsentStore` token (`consent.rs:440-454`, atomic across processes via `DELETE`-rowcount), so a replayed hire fails closed rather than double-charging; the client-side warning remains because the *outcome* is still unknown, which is a query problem, not a safety one. `kanban_panel` generates one key per operator **gesture** (before the retry loop, not per attempt — per-attempt keys would defeat the mechanism entirely) and widens its retry to cover `Interrupted` for exactly `IDEMPOTENT_TOOLS`. Because the panel injects the key into a raw JSON object, nothing ties the two sides together at compile time and a rename would silently disable protection via `#[serde(default)]` — pinned by `wire_field_name_matches_what_clients_send`. Non-durable degradation is labelled (`idempotency_durable: false`) when the kanban DB is in-memory, per the advertised-invariant rule. Pinned by `tests/idempotent_creates.rs` (15, incl. cross-process replay, row-count oracles, and `wire_field_name_matches_what_clients_send`) + `kanban_panel::tests` key-policy tests (the in-crate `idempotency::tests` module was deleted with the condenser teardown; the store's behavior is now pinned end-to-end through the real tool surface, which is the stronger oracle — it fails if either the store or its wiring regresses).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

   - `[workspace.members]` / `[workspace.dependencies]` in root `Cargo.toml`
