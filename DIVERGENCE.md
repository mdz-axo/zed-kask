# DIVERGENCE.md — zed-kask fork divergence from upstream Zed

> **Purpose:** the headline doc for upstream-sync conflict resolution. Every
> `git fetch upstream && git merge upstream/main` consults this file to know
> which crates/files are divergent and why. Referenced from
> `kask/docs/architecture/zed-host-architecture-plan.md` (§13.4).
>
> **Rule:** everything under `kask/` is ours (additive; upstream never touches
> here → near-zero merge conflict). Everything else tracks upstream; the only
> divergences are the D-seams listed below + the `[workspace.members]` /
> `[workspace.dependencies]` arrays in the root `Cargo.toml`.

## The divergence surface (D1–D28)

Every hKask integration maps to a named, isolated change in zed-kask. These
are the _only_ edits to zed-kask's tree outside `kask/`. Any hKask behavior
that would require touching other Zed crates is a smell — push the logic into
an hKask crate behind one of these seams instead.

| D3  | hKask tools in-process                                                                  | `crates/zed/src/main.rs`                                                                                                                                                                                                                                                                                                                             | `McpRuntime` implements `ToolPort` directly (call metering + `reg.tool.*` spans) and is passed wherever a `ToolPort` is needed — no bridge adapter. MCP servers run as child processes (stdio). Daemon transport deleted; identity from `ServerContext.webid` (`HKASK_WEBID`). **`McpRuntime::invoke` performs NO per-call authorization.** The former capability-match gate was deleted 2026-08-12 (RR-0056): all three production mint sites derived the `DelegationToken`'s `resource_id` from the same tool name they passed to `invoke`, so `is_valid_for` compared a caller-supplied value against itself and could not deny — it ran on every tool call and denied nothing while being advertised here as "the enforced gate." `DelegationToken`, `panel_default_token`, `capabilities_match`, `capability_from_server_id`, and `ToolPortError::CapabilityDenied` are gone; `invoke` now takes `agent: WebID` (accounting identity, not a credential). Authority lives at the boundaries whose list the caller does not choose: the inference IPC per-request `tool_allowlist` (fail-closed, D8), the swarm card `mcp_tools` allowlist, and the per-server MCP env/credential allowlists (RR-0038). Pinned by `runtime::tests::{unregistered_agent_is_auto_registered_not_denied, exhausted_ceiling_trips_the_runaway_breaker, no_governance_dispatches_unmetered}` + `tests/invoke_gate.rs`. Settings-change restart: governed McpRuntime instances are started once at login; `sync_kask_mcp_runtime_servers` (a `SettingsStore` observer) diffs each server's computed env (`kask_server_env`) against the launch baseline and restarts changed servers via `McpRuntime::stop_server` + `start_server_with_env`, so e.g. a `kask.swarm.mode` toggle re-routes the governed path; the restart logs the *changed env keys* (never values — several are credentials) because a restart tears down live connections and fails every in-flight panel call, so "env changed" alone could not distinguish a deliberate toggle from a startup-ordering artifact. **Connections self-heal.** A dead connection used to be sticky and unrecoverable: the keeper task's `running.waiting()` arm exited without removing the entry, `start_server_with_env` early-returned on a presence-based `connections.contains_key` check, and `get_peer` handed out the corpse forever — so every call returned `Transport closed` until an operator changed a setting. Four mechanisms now close that loop (`kask/crates/hkask-mcp/src/runtime.rs`): (1) the keeper task reaps its own connection when the service loop exits on its own, guarded by a generation stamp so a late-exiting keeper cannot remove a healthy replacement installed by a reconnect; (2) `get_peer` filters peers whose `is_transport_closed()` is already true, covering the window before the keeper is scheduled; (3) `start_server_with_env` records a `LaunchSpec` so `call_tool_inner` reconnects on demand and retries **once**, bounded by `RECONNECT_COOLDOWN` (5s) so a crash-looping binary cannot become a process-spawn storm; **(4) a per-server health supervisor** checks transport liveness every 60s (`HEALTH_CHECK_INTERVAL`) and proactively removes dead connections before the next tool call discovers them, with a circuit breaker that stops auto-healing after `MAX_CONSECUTIVE_HEALTH_FAILURES` (3) consecutive failures and logs an operator-actionable error. The supervisor does not call `try_reconnect` directly (the future is not `Send`); it removes the dead connection and relies on mechanism (3) for healing. `start_server_with_env` also retries spawn+handshake up to `STARTUP_MAX_RETRIES` (3) with exponential backoff (500ms→10s) before reporting failure, and pipes child stderr to `tracing` with `target: "hkask.mcp.child"` and the `server_id` field for attributed diagnostics. A TOCTOU race between concurrent `start_server_with_env` calls (e.g. startup + on-demand reconnect) is handled by checking at insert time: the loser's keeper is cancelled and its child process killed, the winner's connection is kept. `stop_server`/`shutdown_all` drop the launch spec and clear `health_failures` so a deliberate stop is not resurrected. The idempotency check is now liveness-based, not presence-based. **Retry safety is classified by provable delivery, not by "was it a transport error".** `ToolPortError` gained two variants: `Unavailable` (no live peer accepted the request — the tool provably did not run, so a retry cannot double a side effect) and `Interrupted` (a live peer accepted it and the connection then failed — **the outcome is unknown**). The distinction is forced by rmcp, which reports both a failed send (`service.rs:921`) and a dropped response channel (`service.rs:555,566`) as the same `ServiceError::TransportClosed`: once a request reaches a live peer, a transport loss is not proof of non-delivery. `is_retryable()` is true for `Unavailable` only; `Interrupted` is never auto-retried, at any layer, because doing so would duplicate state-changing effects (two `kanban_task_create`s, a `swarm_hire` charging credits twice). Internally `DispatchError::{NotDelivered, Interrupted, Failed}` carries this, and only `NotDelivered` drives the one-shot reconnect-and-retry. Pinned by `runtime::tests::{unreachable_server_reports_unavailable_not_failed, only_unavailable_is_retryable, interrupted_is_never_auto_retried, interrupted_and_unavailable_are_distinguishable, unknown_tool_is_not_found_not_unavailable, failed_start_still_records_a_launch_spec_for_later_reconnect, stop_server_clears_the_reconnect_path, shutdown_all_clears_every_reconnect_path, reconnect_is_rate_limited_by_the_cooldown, metadata_only_server_cannot_be_reconnected}`. **Healing is verified against real child processes** by `tests/reconnect_integration.rs` (5 tests, `--features test-fixture`), which SIGKILLs a controllable fixture MCP server (`src/bin/mcp_test_fixture.rs`) and asserts the next call reconnects and is served by a *new* pid. Each of the first three mechanisms is independently pinned — verified by mutation: disabling reconnect-on-demand fails `killed_server_is_reconnected_on_the_next_call`, and disabling reap+liveness fails `dead_connection_is_reaped_from_the_runtime`. The fourth mechanism (health supervisor) and the startup retry/stderr capture are not yet independently pinned by mutation tests — a follow-up should add a test that kills a server, waits >`HEALTH_CHECK_INTERVAL`, and asserts the supervisor removed the connection without a tool call. The fixture's kill path uses `libc::kill` and **asserts** success, because an earlier version that swallowed the result with `let _ =` made the whole suite pass vacuously with all healing disabled. **Server-side replay protection resolves the `Interrupted` ambiguity for the three tools that cannot absorb a duplicate.** `Interrupted` is unavoidable at the client, so it can only be *resolved* at the server: `hkask-mcp-kata-kanban/src/idempotency.rs` stores `(tool, key) → first response` in the kanban database, and `kanban_task_create` / `kanban_board_create` / `kanban_task_spawn` accept an optional `idempotency_key` and return the original response (plus `replayed: true`) instead of re-running. The claim is a single `INSERT OR IGNORE` whose zero-rowcount *is* the already-seen signal, so two concurrent replays cannot both win — no read-then-write race, and no transaction (`dyn DatabaseDriver` exposes none). Reservation is two-phase (`reserve` → work → `record`) because the work happens between: a key claimed but never recorded is `Pending`, reported as unknown rather than silently re-run, since whether it landed is precisely what is unknown; a cleanly-failed call calls `release` so a retry starts fresh instead of inheriting that verdict. Only these three needed it — `task_update`/`task_assign`/`task_delete`/`board_delete` already converge, and `swarm_clone_to_local`/`swarm_push_to_cloud`/`swarm_create_local_agent` are keyed by `agent_name`. **`swarm_hire` was already protected** by `spend_gate`'s consume→spend→refund over a single-use `ConsentStore` token (`consent.rs:440-454`, atomic across processes via `DELETE`-rowcount), so a replayed hire fails closed rather than double-charging; the client-side warning remains because the *outcome* is still unknown, which is a query problem, not a safety one. `kanban_panel` generates one key per operator **gesture** (before the retry loop, not per attempt — per-attempt keys would defeat the mechanism entirely) and widens its retry to cover `Interrupted` for exactly `IDEMPOTENT_TOOLS`. Because the panel injects the key into a raw JSON object, nothing ties the two sides together at compile time and a rename would silently disable protection via `#[serde(default)]` — pinned by `wire_field_name_matches_what_clients_send`. Non-durable degradation is labelled (`idempotency_durable: false`) when the kanban DB is in-memory, per the advertised-invariant rule. Pinned by `idempotency::tests` (8) + `tests/idempotent_creates.rs` (13, incl. cross-process replay and row-count oracles) + `kanban_panel::tests` key-policy tests; verified by mutation — disabling `with_idempotency` fails exactly the 5 duplicate-prevention tests while the 6 asserting unprotected behavior still pass.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

## Governing invariant (§13.1)

**hKask crates NEVER depend on zed-kask crates; zed-kask depends on hKask.**
The sole bidirectional seam is `kask_bridge` (D8), which lives under
`kask/crates/` and depends on both sides. Enforced by
`kask/scripts/check-hkask-no-zed-deps.sh` (wired into CI).

## Upstream-sync runbook

1. `git fetch upstream && git merge upstream/main`
2. Conflicts will only appear in:
   - The D-seam files listed above (D1–D27)
   - `[workspace.members]` / `[workspace.dependencies]` in root `Cargo.toml`
   - Modify/delete conflicts — upstream may restore files zed-kask deliberately
     deleted under D7/D16 (icons, `.desktop` templates, bundle scripts, release
     workflows). Resolve by re-deleting; verify with
     `bash kask/scripts/build/check-zed-isolation.sh`.
3. Everything under `kask/` is additive → never conflicts.
4. After resolving, run `bash kask/scripts/check-hkask-no-zed-deps.sh` to
   verify the §13.1 invariant still holds.
5. Run `cargo check -p kask_bridge -p hkask-types -p hkask-mcp-server` to
   verify the bridge + foundation still compile.
6. Run `bash kask/scripts/build/check-zed-isolation.sh` — verifies deleted
   upstream surfaces (icons, `.desktop` templates, bundle scripts, release
   workflows) were not silently restored by the merge. Wired into CI
   (`kask-ci.yml` invariants job).
7. Run `./script/clippy` (per `.rules` build guidelines — use this instead of
   `cargo clippy`; runs under `--deny warnings`). A `rust-toolchain.toml` bump
   may promote previously-allowed lints to denied — clippy catches these.
