## Storage and credentials

- **DB:** `{kask_data_dir}/mcp/kata-kanban/kanban.db` (D28 layout; override
  via `HKASK_KANBAN_DB`, a non-secret config path read via `config_env`).
  SQLCipher via `hkask_storage::open_or_repair` — the server **requires**
  `HKASK_DB_PASSPHRASE` and refuses startup without it (the
  `kanban_startup_requires_durable_storage` pin: missing durability is an
  explicit startup failure, never a volatile fallback). Replay protection
  (`idempotency.rs`) shares the same database, so protection has the same
  durability as the writes it guards.
- **Credential declaration:** `CredentialRequirement::required("HKASK_DB_PASSPHRASE")`
  — the `.rules` reference pattern for DB-backed servers.

## Surfaces

- **Boards:** create (idempotent), list, delete (owner-gated,
  `permission_denied`), rename (owner-gated), mermaid export/import
  (round-trip pair; import is replay-safe and atomic).
- **Goals:** MCP create/judge/get/list/trust-record only. Create requires real specification
  `source: { interaction_id, session_id, source }`, immutable criteria, optional
  `supersedes`, and an optional typed `forecast`, not routine `prediction`.
  Every goal carries a standing trust clause (`GoalTrustClause`) as part of
  the spec digest; a caller who omits it gets the default (Butler–Giuliano–Guiso 2009;
  Akerlof 1970; Slovic 1993; Kim–Ferrin–Cooper–Dirks 2004; Fuller–Perdue 1936–37).
  Create/get return full aggregates with `id`, `criterion_ids`, `spec_digest`,
  `trust_clause`, `trust_events`, and the computed `trust_summary`;
  list returns an array of those aggregates (`Vec<Goal>`), including closed goals.
  Judge appends worker progress, never human acceptance. Trust-record
  (`kanban_goal_trust_record`) appends a `GoalTrustEvent` to the goal's running
  trust ledger and returns the updated `trust_summary` — the regulation signal
  (seam 7). Native host `kanban_goal_close` takes `goal_id` and evidence only
  and obtains the six-way accomplished/stop × achieved/not-achieved/unknown
  decision via human `ActionChoice`. Native `kanban_goal_correct_outcome`
  is a separate authenticated append-only correction. These are not MCP
  routes. Canonical history persists after current-state indexing; no
  prune-on-ack. See `kask/mcp-servers/hkask-mcp-kata-kanan/GOAL_INTERFACE.md`
  for exact types.
- **Tasks:** create (idempotent; goal-criterion citations validated at
  creation), update (owner-gated), list, move (status transitions; the
  Algedonic review board requires `kanban_task_verify` in Review to reach
  Done), assign/unassign, delete, verify (evidence text is the pass
  signal), comment/comments-since (the subagent↔agent feedback thread and
  the incremental memory-ingestion channel), add-deliverable, reopen,
  kata-prompt, spawn (worktree-isolated via the parent-authorized
  `WorktreeSpawnPort`; a missing grant or uncertain reply never starts a
  fallback), delegate-result (the structured verdict readback).
- **Idempotency:** `with_idempotency` — three-outcome replay semantics
  (fresh / replay-verbatim / refused-pending), fail-closed reservation,
  the post-effect rule (bookkeeping failures fold into the response;
  releasing the claim would let a retry duplicate the effect), and the
  spawn special case (an `Unavailable` spawn may have landed; the pending
  claim stays).

## Assessment and recall

The [canonical goal contract](../../../mcp-servers/hkask-mcp-kata-kanban/GOAL_INTERFACE.md)
owns evidence consent/bounds, blinded assessment, optional `HumanAcceptance`
forecasts and recovery. Human judgment is required; scoring administration is not.
The bridge calls `goal_assess` and `goal_index_current`: coordination stays private
to the service, while capture and inference use the existing boundaries directly.
One current recall record replaces per-event delivery history. Only schema 3 is
accepted. `goal_list(owner)` checks caller ownership before decoding and returns
`Vec<Goal>`; `goal_scan_for_host()` returns `HashMap<WebID, Vec<Goal>>`.
Invalid current records and query failures are visible errors, not omissions or
rejection maps. Obsolete goal rows and recall projections are discarded by an
explicit one-time reset, not runtime migration or archival compatibility. No reset
execution is claimed here.
Scheduling remains gated by `curator.always_on`; missing capabilities and failed
work remain visible and retryable. Canonical history is never deleted by indexing.
