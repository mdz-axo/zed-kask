## Storage and credentials

- **DB:** `{kask_data_dir}/mcp/kata-kanban/kanban.db` (D28 layout; override
  via `HKASK_KANBAN_DB`, a non-secret config path read via `config_env`).
  SQLCipher via `hkask_storage::open_or_repair` — the server **requires**
  `HKASK_DB_PASSPHRASE` and refuses startup without it (the
  `kanban_startup_requires_durable_storage` pin: missing durability is an
  explicit startup failure, never a volatile fallback). Replay protection
  (`idempotency.rs`) shares the same database, so protection has the same
  durability as the writes it guards.
- **Credential declaration:** `CredentialRequirement::required("HKASK_DB_PASSPHRASE")`
  — the `.rules` reference pattern for DB-backed servers.

## Surfaces

- **Boards:** create (idempotent), list (carries the per-database
  monotonic change counter — poll it to skip re-fetching unchanged
  state, the kanzo P1 pattern), delete (owner-gated,
  `permission_denied`), rename (owner-gated), mermaid export/import
  (round-trip pair; import is replay-safe and atomic, and is refused with
  nothing created when a column lists more tasks than the WIP limit it
  declares or a task title is blank).
- **Goals:** MCP create/judge/get/list only. Create requires real specification
  `source: { interaction_id, session_id, source }`, immutable criteria, optional
  `supersedes`, and an optional typed `forecast`, not routine `prediction`.
  Create/get return full aggregates with `id`, `criterion_ids`, `spec_digest`;
  list returns an array of those aggregates (`Vec<Goal>`), including closed goals.
  Judge validates a reported verdict against the frozen criteria and advances
  the goal's revision; no verdict is stored, and human acceptance is never
  implied. Native host `kanban_goal_close` takes `goal_id` and evidence only
  and obtains the six-way
  accomplished/stop × achieved/not-achieved/unknown decision via human
  `ActionChoice`. Native `kanban_goal_correct_outcome` is a separate
  authenticated append-only correction. These are not MCP routes. Canonical
  history persists after current-state indexing; no prune-on-ack. See
  `kask/mcp-servers/hkask-mcp-kata-kanban/GOAL_INTERFACE.md` for exact types.
- **Tasks:** create (idempotent; goal-criterion citations validated at
  creation), update (owner-gated; carries the operator-reserved marker —
  claim tools and compact listings skip reserved tasks with a disclosed
  count), list (full `TaskInfo` objects, or `view=compact` for
  token-frugal one-struct summaries with Done capped at 20 and reserved
  tasks skipped, both disclosed by count), move (status transitions; the
  Algedonic review board requires `kanban_task_verify` in Review to reach
  Done), assign/unassign, claim-next (the pull primitive: one transaction
  assigns the caller and moves the oldest unassigned Ready task to In
  Progress, skipping reserved tasks and honoring the In Progress WIP
  limit; replay-protected by an optional idempotency key), delete, verify
  (evidence text is the pass signal), comment/comments-since (the
  subagent↔agent feedback thread and the incremental memory-ingestion
  channel), add-deliverable, reopen (passes the In Progress WIP
  admission), kata-prompt, spawn (worktree-isolated via the
  parent-authorized `WorktreeSpawnPort`; takes the task and the skills to
  name in the child's prompt and refuses any other field; a missing grant
  (`host/create_worktree_thread` for this server under
  `kask.mcp.delegated_tools`) is `permission_denied` naming it; a missing
  grant or uncertain reply never starts a fallback, and a spawn that did not go
  through leaves no comment on the task).
- **Who may read and write:** mutations check the caller (task owner or
  assignee; owner alone for delete, verify, reopen, unassign, update and
  spawn; board owner for rename, delete and export). Task reads and task
  creation on a board do not: list, comments-since, kata-prompt and create
  answer any caller holding the id. Deliberate (operator ruling
  2026-11-11), pinned by
  `task_reads_and_task_creation_are_open_to_any_caller`, and moot while
  the server runs as one fixed identity (the bridge passes `HKASK_WEBID`
  only to the curator server). Revisit if callers get distinct identities.
- **Idempotency:** `with_idempotency` — three-outcome replay semantics
  (fresh / replay-verbatim / refused-pending), fail-closed reservation,
  the post-effect rule (bookkeeping failures fold into the response;
  releasing the claim would let a retry duplicate the effect), and the
  spawn special case (an `Unavailable` spawn may have landed; the pending
  claim stays). `kanban_task_claim_next` also takes a key — a replay
  would claim a SECOND task, which is effect-duplicating even though the
  pull mints no identity.

## Assessment and recall

The [canonical goal contract](../../../mcp-servers/hkask-mcp-kata-kanban/GOAL_INTERFACE.md)
owns evidence consent/bounds, blinded assessment, optional `HumanAcceptance`
forecasts and recovery. Human judgment is required; scoring administration is not.
The bridge calls `goal_assess` and `goal_index_current`: coordination stays private
to the service, while capture and inference use the existing boundaries directly.
One current recall record replaces per-event delivery history. Only schema 3 is
accepted. `goal_list(owner)` checks caller ownership before decoding and returns
`Vec<Goal>`; `goal_scan_for_host()` returns `HashMap<WebID, Vec<Goal>>`.
Invalid current records and query failures are visible errors, not omissions or
rejection maps. Obsolete goal rows and recall projections are discarded by an
explicit one-time reset, not runtime migration or archival compatibility. No reset
execution is claimed here.
Scheduling remains gated by `curator.always_on`; missing capabilities and failed
work remain visible and retryable. Canonical history is never deleted by indexing.
