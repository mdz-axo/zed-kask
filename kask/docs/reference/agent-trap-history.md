# Agent trap history — the retired `.rules` corpus (archived 2026-11-06)

This is the accumulated worktree-root trap corpus, retired the same day by
operator ruling (option "radical simplification", 2026-11-06): the corpus
was context-injected into every session and demonstrably did not prevent
the failures it described — its volume multiplied evasion surface and
per-session token cost without purchasing good faith. It is preserved
here as reference history: consult it when relevant (grep on demand); it
is NOT context-injected and binds nothing. The distilled intent statement
that replaces it lives in the worktree-root `.rules`.

The content below is the verbatim bytes as they stood at retirement,
including the enforcement entry added earlier on 2026-11-06 (the
data-dirs gate named there was removed by the same simplification ruling —
script, selftest, and CI wiring; the intent it encoded stays in the
distilled `.rules`).

# Agent discipline

* When the requested outcome is a working capability (a skill, pipeline, or process), the deliverable is the capability functioning — verified by running the task through it — not hand-completion of the instance task. "Cowboying a solution" is failure even if the artifact ships (operator ruling 2026-09-09).
* Completion records cite commit hashes, not intentions — "done, all tests green" before the commit exists has outrun the tree. Name the hash, or say the work is uncommitted (observed 2026-09-08).
* A coding task that only adds is not done (PRINCIPLES P5.5, operator ruling 2026-09-26): name what the change replaces and delete it — old paths, copied pattern instances, tests of removed behavior — in the same change, and report net lines.
* An expectations-gap capability benchmark is a load-bearing design choice, never a silent convention: a >4x revenue window is an episode, not a repeatable capability; never hand-derive a benchmark in-conversation when zk-ref-open carries the published model (sustainable-growth-rate.md, expectations-investing.md) — and check the data path that feeds the model.
* A verification claim does not carry into the next commit message without its oracle re-run — the oracle that adjudicated the prior claim (a pin test, a gate) must run against the change the new message describes; a claim inherited from an earlier green state is a fabricated attestation (observed 2026-10-29: t6–t9 commit messages asserted "panel pin green" while the cross-crate panel pin was red from t7 onward; `cargo test -p <server>` never executes the consumer crate's pin).
* An operator-facing reading surface must be verified to exist in the same turn it is offered — "read X" or "the evidence is yours" sent without a fresh existence check (`ls`, `wc -l`) of X in that turn is a fabricated pointer, the same class as "done, all tests green" before the commit exists. The handoff message itself must carry its own verification: the surface's path, its line count, and a re-runnable command the operator can execute independently. Observed twice in one session (2026-11-01, the stage-1 adjudication gap): the operator-facing adjudication input the runbook promised did not exist when the operator was twice sent to read "the evidence"; the operator had to catch the gap manually and call it out. A double failure: the deliverable was skipped AND no instrument caught the skip.
* An arXiv id resolved through `resolve_paper` with no title metadata is a valid id, not a typed identity — the id-echo (canonical URL returned, no OpenAlex record) proves the id exists, never that it names the intended work. Title-verify before putting an id in a citation position (resolve by title and check the returned candidates, or corroborate the id against a second source), and apply the same check to ids inherited from another record — a citation copied from a doc is a claim needing the same verification as your own research (two specimens in one arc, 2026-11-02: Amodei et al., Concrete Problems in AI Safety, resolved blind as arXiv:1606.06524 — the true id is 1606.06565; and goal-reference-models.md's "André et al. 2023" cited arXiv:2305.19152, which resolves to an unrelated quant-ph paper — caught only when independent verification pulled the id).

# Corpus pipeline traps

* `corpus_tag_chunks` `tag_batch_size` default is 10; `extract_json_from_response` (`hkask-types/src/json_extract.rs`) must return the full JSON array, not just the first object — first-`{`-only parsing silently fails batching (1/N chunks get real tags per LLM call). Test: `extract_json_from_response("[{\"a\":1},{\"b\":2}]")` returns the full array.
* `corpus_build_prompts` `max_pairs` default 0 means all chunks × `qa_pairs_per_chunk` — leave it at 0 or set `tagged_count × qa_pairs_per_chunk`; 500/600 on a 33K-chunk corpus produces a toy dataset.
* QA quality verification checks SEMANTICS, not just structure: boilerplate contamination, grounding-verify provenance/substring discipline, Bloom distribution evenness, subject diversity.

# Duplication ratchet

* jscpd 5.4.0's JSON reporter emits file names as path SUFFIXES — bare basenames for explicitly-passed files, partial paths for directory-scanned ones — never repo-relative paths. Resolving a report name as a repo-root path silently fails the upstream existence check and misclassifies upstream files as fork-owned (observed live: the R5 triage's first pass read 1403 clusters as fork-owned vs the true 675). Resolve report names by unique-suffix match against the scan set; ambiguous suffixes surface as multiple visible candidates and need explicit disambiguation, never a repo-root guess.

# Structural analysis (ast-grep)

* An ast-grep pattern in TYPE position needs `context`+`selector` — a bare `Result<$T, String>` pattern parses as a comparison expression (`a < b, c > d`) and matches NOTHING, silently. A "0 instances" scan is consistent with both a clean surface and a broken rule: pin every rule with a positive fixture (a synthetic violation it must catch — the `check-*-selftest.sh` pattern) before trusting zero (live 2026-10-11: the string-errors rule shipped broken while the real surface read "0 instances").
* Path:line ratchet baselines drift under concurrent streams — a line-shifting edit in another stream's commit shows as equal net-new and stale counts (same instances, moved lines). Equal counts are the drift signature: confirm by per-file instance totals, absorb by refreshing the baseline in the commit that earns it (live 2026-10-11: 111 net-new / 111 stale, 468 instances both sides).

# Rust coding guidelines

* Project scripts are bash, not Python — audit/build scripts live under `kask/scripts/` as bash. Python (dynamically typed, interpreted — no static guarantees, an interpreter dependency inside CI gates, mediocre LLM codegen quality) is out of bounds everywhere under `kask/` and fork-owned workflows: no standalone `.py`, no `python3` heredocs or invocations inside bash scripts, no Python tooling declared. Parsing bash cannot do belongs in a Rust test or bin on workspace deps (`toml`, `serde_yaml_neo`) — never an embedded interpreter. Enforced by `kask/scripts/check-no-python.sh`; exceptions only via its explicit allowlist, each a recorded operator decision. Upstream-owned surfaces (`script/`, `crates/eval_cli/`, `nix/`, upstream workflows) are recorded, not gated. (Operator ruling 2026-10-13, tightening 2026-09-09.)
* The zero-Python boundary is project-wide for anything an agent authors (operator ruling 2026-11-06, extending 2026-10-13 past the repo tree): no Python in the data dirs (`~/Documents/zk-data`, the hidden data dir), replication workspaces, or "temporary" research tooling — the language choice is surfaced to the operator BEFORE building, never tagged after the fact; ecosystem convenience (e.g. PyTorch for weight-space work) is a surfaced capability gap, not an exception. Enforced past the repo boundary by `kask/scripts/check-no-python-data-dirs.sh` (selftest-pinned; pinned upstream trees and corpus code-as-data are recorded, not gated).
* No `unwrap()` in production code — use `?` to propagate errors; in test code prefer `expect` with a message.
* Never silently discard errors with `let _ =` on fallible operations. Propagate with `?`, use `.log_err()` for visibility, or handle explicitly.
* No `mod.rs` files — use `src/module.rs` instead (CI: `check-no-mod-rs.sh`, fork surface).
* New crates: specify `[lib] path = "..."` in `Cargo.toml` (e.g., `gpui.rs`, not `lib.rs`).
* Build: use `./script/clippy` instead of `cargo clippy`.
* `str::split_once` CONSUMES the delimiter: `"500ms".split_once('m')` yields `("500", "s")` — the delimiter is in neither half. For (prefix, suffix) extraction use `find()` + `split_at()`. Hit live: retry-after parsing silently read 500ms as 500s.
* Exported `macro_rules!` must `$crate`-qualify every internal path — textual `crate::`/`super::` in a `#[macro_export]` body resolve at the invocation site, so the macro compiles in its home crate and breaks any cross-crate caller (live: `impl_from_db_error!`'s `super::database::…` worked one level under the storage root, E0433 from hkask-mcp-media). Submodule items need a root re-export for the `$crate` path (the `DatabaseDriverTrait` alias pattern, `store_macros.rs`).

# Timers in tests

Use `cx.background_executor().timer(duration).await` in GPUI tests, not `smol::Timer::after(...)` — smol timers aren't tracked by GPUI's scheduler and break `run_until_parked()` (CI: `check-no-smol-timer.sh`, GPUI-side fork surface).
* In tokio tests, `#[tokio::test]`'s default current-thread runtime + a blocking synchronous wait loop starves any spawned task whose progress the test is waiting to observe — the test can never observe the condition. Use `#[tokio::test(flavor = "multi_thread", ...)]` or async waits (`tokio::time::sleep(...).await` loops) whenever a test must observe a spawned task's progress; every landed tokio suite that does runs multi-thread (the private-inference supervisor-stub/live suites, hkask-mcp's reconnect suite).

# Agent crate (crates/agent)

* `cache_read_input_tokens` is served from the provider's prompt cache at ~0.1x cost — do NOT count it toward compaction thresholds. Use `billed_input_tokens` (input + cache_creation) for cost-driven decisions like compaction; use `total_input_tokens` only for context-window-overflow warnings. Mixing these causes premature compaction of nearly-free cached context.
* The system prompt is cached on `Thread` keyed by a SHA-256 digest of its inputs (`render_system_prompt`). Do NOT bypass this by rendering `SystemPromptTemplate` directly — bypassing it breaks the byte-stability that lets the provider's prefix cache hit.

# GPUI traps

* No `block_on` on the foreground thread — it deadlocks if the future needs the GPUI or tokio executor. Make the method async instead.
* Don't use `Arc::get_mut` on `Thread.messages` — it returns `None` when shared. Clone the inner value, modify, replace the `Arc`.
* Don't busy-spin or use timers to wait for deferred tool results in `end_turn` — let the turn end; results drain on the next iteration.
* `AsyncApp` is not `Send` — background tokio tasks must use `tokio::sync::mpsc` channels with a foreground drainer, not capture `AsyncApp`.
* `cx.background_spawn` panics on tokio-dependent futures (reqwest, tokio::time, etc.) — use `gpui_tokio::Tokio::spawn(&*cx, ...)` instead.
* `tokio::time::timeout` / `tokio::time::sleep` panic inside `cx.spawn` (foreground) tasks — `tokio::time::Sleep` registers with the tokio reactor's timer wheel at poll time, and no tokio reactor is entered on the GPUI foreground thread. Race a GPUI-native timer instead: `cx.background_executor().timer(duration)` + `futures_util::future::select`. `tokio::select!` + `mpsc::recv()` is safe (mpsc receivers are executor-agnostic).
* Center-pane `Item` Toggle must use `Toggle` action (not `ToggleFocus`). After `add_item_to_active_pane`, explicitly call `page.focus_handle(cx).focus(window, cx)` if focus delegates to a child entity.
* A consumer crate's committed test/bench fixture is NOT under the media
  widget's approved roots: `PathMediaStorage`'s cfg(test) root is the WIDGET
  crate's own `test_data/` (the defining crate's compile-time
  `CARGO_MANIFEST_DIR`), and a consumer's test binary compiles the widget
  WITHOUT cfg(test) — the consumer's fixture resolves only after explicit
  `approve_gallery_media_path` registration (the same gallery-result path
  authority production ingest uses; precedents:
  `hkask-media-benchmarks/benches/playback.rs`, media_panel
  `viewer_layout_tests::admit_fixture`). The fixture must also preserve the
  adversarial properties its consuming test documents — a 160×120 fixture kept
  `viewer_content_fits_narrow_pane` green while gutting its wider-than-pane pin
  (live 2026-11-05, the vacuous-green class).

# Pull request hygiene

- Imperative PR title, no conventional commit prefixes, no trailing punctuation.
- `Release Notes:` section as final section, blank line after heading, one bullet (`- Added/Fixed/Improved/N/A`).
- Commit messages are plain text at the `git commit` boundary — never include the markdown fences used to present the message in chat; a bare ``` first or last line leaks into the commit subject (97 commits on main, 2026-07→09). The `kask/githooks/commit-msg` hook (wired via `git config core.hooksPath kask/githooks`) rejects fenced messages.

# Rules hygiene

* `.rules` are traps to avoid, not maps to follow. No architectural descriptions.
* New rules must be: non-obvious, repeatedly encountered, and specific enough to act on.
* Only the worktree-root `.rules` is loaded into agent context (`load_worktree_rules_file`, `crates/agent/src/agent.rs`); a nested `.rules` is never read. Keep crate-scoped traps here under a crate heading, stated as one actionable constraint each.
* Don't edit `.rules` inline during feature work — propose additions in the change report or a dedicated rules-only commit.

# Agent loop traps

* **Tool-call arguments cut mid-JSON surface as a typed truncation error — resend the whole call, never proceed on a partial argument set.** Every provider mapper classifies an EOF-shaped argument fragment (`EOF while parsing …`) as `ToolCallTruncated`: non-retryable, names the tool and the cut, nothing dispatched, no tool-failure budget consumed. Absent optional fields ≠ truncation — required fields reject visibly, and complete JSON with absent optionals is deliberate omission. A request rejected as too large (`endpoint maximum context exceeded`) is prompt-size, not output truncation: pass file paths, not contents.
* A failed `edit_file` call changes nothing (D78) — retry the whole call; scope every `old_text` to be unique, since a repeated match fails the call.
* `edit_file` does not reject near-miss `old_text` — the fuzzy matcher applies it anyway and reports success, so the corruption first surfaces at build or doc-test time (D78 covers the failed-call class; this is the successful-but-corrupting class). Copy `old_text` verbatim from a fresh read of the exact current region (observed 3× 2026-10-23 plus the prior session: a dropped `)` broke the build, a `Comment` lost from a `use` re-export hit E0432, a 4-backtick doc fence normalized to 3 broke rustdoc doctests — every call reported success).
* Escape-sequence regions double the near-miss risk: transcribing `old_text`/`new_text` through the tool-call JSON can silently under-escape backslash sequences (Rust `\n\` string-literal continuations, regexes) — the fuzzy matcher accepted a match missing the `n`s and the closing quote, and the corruption surfaced only at compile (4th same-day specimen 2026-10-23: E0765 quote-parity shift behind 35 cascade errors). After any edit whose old/new text contains backslash escapes, re-read the landed bytes (grep the anchor) before compiling — a successful `edit_file` call over such a region is corruption-prone until byte-verified.
* A successful `edit_file` report is not proof of landing — after a multi-hundred-line structural edit, verify the file actually changed (git status/diff) before building on it: two success-reported calls landed zero bytes on their target file in one session (2026-10-31), caught only because a tree check was in the flow; the next compile would have failed with a misleading gap.
* A successful `edit_file` call can land a different byte arrangement than its `new_text` specifies — inserted `mod`-declaration pairs landed alphabetized rather than in the given order in two live specimens (2026-11-01 layers walk), each call reporting success; the follow-up insert's byte-assumed `old_text` then failed to match the very lines the previous call had just written (the same class was proposed from the prior session's receipts). Never chain byte-assumed `old_text` across `edit_file` calls on the same file — re-read the landed anchor (grep it) before composing the next edit.
* **Composition breaks at the seam, not the stage.** Verify stage N's output shape is what stage N+1 consumes *before* running the chain — wrong-shape reads fail silently (serde ignores a misplaced field) or partially (a first-`{` parser drops the array rest; a model under a huge prompt supplied 3 of 8 parameters). Round-trip or count-reconciliation checks catch seam breaks; eyeballing the shapes does not. A multi-reader wire format is the same trap at rest: every reader consumes the one decode home (the type owner's), and a reader-side inline decode is a fork even when its values agree today — enumerate the READER set when consolidating a format, not just the writers.
* `lisp_eval` `string-contains` takes (needle, haystack) — needle FIRST: `(string-contains "clear market leader" "abc clear market leader xyz")` → true. Reversed args return false silently (and error naming the probable reversal when the first arg is longer than the second — the guard); a 20-quote verification batch with reversed args failed every check while all quotes were verbatim substrings (2026-09-28 YETI run; first mis-filed as a tool bug). Convention follows assoc/member, documented at `kask/crates/hkask-lisp/src/hkask_lisp.rs`.
* `grep`/`find_path` include patterns and globs must start with `**/` or the project-root directory name — a bare `kask/docs/**` or `crates/agent/src/**` matches zero files and wastes the call (observed 3× 2026-09-27/28: the docs D/P sweep, the template-dir find, the retry-tracker call-site grep — each read as “nothing there” while the files existed). Both tools now append a wrong-root warning naming the corrected form when the pattern provably matches nothing (D81), but the warning arrives after the wasted call — write the pattern correctly the first time.
* `rg -rn '<pattern>' <path>` parses as `-r n` — replace every match with the literal `n` — and the command silently returns rewritten output instead of erroring (observed 2026-10-28 and 2026-11-02: a claim_next tool grep and an earlier sweep both displayed substituted text; the flag typo cost a re-run each time). For line-numbered matches use `rg -n`; use `-r` only with an explicit replacement string.
* A source grep over one crate cannot see tests a `macro_rules!` in another crate generates into it — the macro’s body lives only in the defining crate (live 2026-11-02: the kata-kanban review declared `tool_names_match_live_router` nonexistent from a source grep over the consuming crate; the `tool_surface_pin!` macro at `kask/crates/hkask-mcp-server/src/hkask_mcp_server.rs:80-96` emits it into every server). Before declaring a test or pin nonexistent from a grep zero, check the macros the target crate invokes — `rg -n 'macro_rules!' <defining crate>` — and if the name is macro-generated, confirm via the macro body or the compiled test list (`cargo test -- --list`), never by source grep alone.
* The built-in `grep` tool skips dot-directories — a repo-wide sweep never sees `.agents/skills/` (observed 2026-10-30: three live consumers of the deleted `sankey-flow` skill were invisible to a repo-wide grep; only `check-skill-crossrefs.sh` caught them). Sweep `.agents/` via `rg --hidden` in the terminal, and treat `kask/scripts/check-skill-crossrefs.sh` as the authoritative sweep for deleted-skill references.
* Goal custody is service-owned since the D58 cutover (2026-10-20) — verify goal delivery by the CURRENT chain shape, never the removed one. MCP routes are `kanban_goal_create`/`judge`/`get`/`list` only; scoring plus the ONE `curator:goal:<id>` / `current` recall row are published inside the service's `goal_assess`/`goal_index_current` through `kask_bridge::GoalHost`, drained on a schedule gated by `curator.always_on` — not at turn end. Read delivery health from the goal record itself (`indexed_revision` trailing `revision` = unindexed work) or from `goal_list` (invalid current records fail visibly), never by grepping memory rows.
* Kanban state moves for the same task race each other inside one parallel tool batch — a batched backlog→ready + ready→in_progress pair fails the second call with "invalid state transition" naming the pre-move state: both calls read the task before either mutation lands (parallel batch calls do not execute in order — the same race class as the file read/edit batch trap under Other traps). One state move per task per batch (observed 3× 2026-10-09 in the D/P enforcement execution; reproduced under control against the rebuilt server the same day).
* kanban_task_comment raced with a same-task move in one parallel batch silently REVERTS the move — the comment's row write lands last and restores the stale status (observed live 2026-10-11 on the test-suite-refresh board: the move returned new_status=ready, the subsequent board listing showed backlog with the comment present). One row-mutating kanban call per task per batch, comments included; post a comment only in a batch carrying no other mutation for that task.
* A failure signal is coarser than the question — localize by capture, never by the message. Sibling code paths mapping failures to byte-identical strings defeat error-text localization — reproducing the message proves the request shape, not the call site; pin the failing leg by capture (a mock port recording which trait arm served), never by error text. Same coarseness the other way: the `tool_reliability` sensor counts agent-input refusals, so read the `error_kinds` breakdown before diagnosing the tool — `failed_precondition`/`not_found` from your own malformed call reads as tool degradation (2026-10-13: 5 not_found were two agent-session parallel batches, card 9657506c; 2026-10-19: a self-inflicted invalid kanban move surfaced as tool_reliability 78, card ae406113).
* A one-character task/card id typo returns not_found from every id-typed kanban tool while the store is healthy — resolve the id against a board-scoped `kanban_task_list` before diagnosing store corruption (2026-10-09: …02f3f331c8c9 vs …02d3f331c8c9 cost a sqlcipher forensic pass to refute).
* STT output is the model's claim about the audio, not evidence a person spoke — on near-silence the STT fabricates words (a 15s low-energy capture transcribed to "Okay. Thank you. Thank you. Thank you." with byte-identical word timings on re-run, mean −29.3 dB); probe energy (ffmpeg volumedetect) or ask before attributing transcript words to a person (observed 2026-10-29/30: the mic smoke leg's "you spoke" claim, retracted after audio forensics; the model-selection report independently run-verifies "hallucination during silence").

# zed-kask integration traps

## Divergence surface

* `DIVERGENCE.md` defines what's ours (`kask/`) vs upstream Zed. Don't "fix" upstream files speculatively — push fixes into `kask/` behind a D-seam; an unavoidable upstream edit carries its D-seam entry + test in the same change. Every `// zed-kask:` comment disabling upstream behavior needs a test pinning the disabled behavior.
* A zed-side edit carries its DIVERGENCE.md seam update in the same pass — an unrecorded zed-side change is indistinguishable from upstream drift at the next rebase.
* `cargo machete` in `script/clippy` stays scoped to `kask/` on purpose — root scope flags ~30 upstream deps as macro/feature-activated false positives, and silencing them means editing ~30 upstream Cargo.tomls (rebase friction) while masking genuinely-dead deps. A machete finding in `kask/` is always actionable: verify zero `use <dep>` hits in `src/` and `tests/`, then remove the dep line.
* A DIVERGENCE.md file-coverage reconciliation must expand brace-shorthand path groups (`{a,b}.rs`) before declaring a file uncovered — the register's compact style (`crates/language_models/src/provider/{anthropic,anthropic_compatible,bedrock,opencode}.rs` under D83) reads as absence to an exact-string check and manufactured four false unregistered-edit findings (2026-10-23 audit).
* Removing a registered action (or its defining crate) must sweep `assets/keymaps/*.json` in the same change — a stale built-in binding fails the startup keymap load and, before D96's degradation, crash-looped the app (live 2026-10-06 collab removal; 2026-10-28 swarm removal, two failed starts). After any action removal run the `cargo test -p zed keymap` set — `test_keymap_assets_only_bind_registered_actions` walks every keymap asset — before the operator rebuilds.

## Failure signals

* Every `set_*` hook wired conditionally must `log::warn!` on failure — operators can't distinguish "not configured" from "configured but broken" without it. `OnceLock` hooks must warn on the `Err` branch of `set`; `Mutex` hooks are re-settable and don't need it.
* Numeric env vars that fail to parse must `log::warn!` naming the malformed value, not silently fall back.
* Opt-in `HKASK_USE_*` features that fail must log the failure classification (HTTP status, error variant), not collapse to `None` via `.ok()?`.
* `unwrap_or(0)` on regulation-loop sense inputs is a broken feedback loop — a DB outage returns 0, which the loop reads as "no deviation." Propagate the error or emit `tracing::warn!`.
* `curator_report_skill_use_issue` is for failures and unexpected output — never file an expected TDD red state or a correct absence as an incident; expected states are verification evidence, not log noise (16 expected_absence rows diluted the 276-row 10-02..10-25 log).

## Skill system

* A skill's missing reference model, D/P label or calibration step is a review finding, never a load-time failure — an incomplete skill must not become a broken skill (operator ruling 2026-09-28). Enforce these in `skill-maintenance` and the corpus audit scripts, not in `agent_skills` loading.
* `lisp_eval` tool — registered in `add_default_tools`. Do NOT register it again in `register_session` — causes "Duplicate tool name" panic.
* `render_template` tool — registered in `add_default_tools` (alongside `lisp_eval`). Path traversal protection via `canonicalize` + `starts_with` — do not bypass this check. Template base path wired via `agent::set_template_base_path()` (OnceLock) in `main.rs` at startup; if not wired, the tool errors — it never silently renders from the wrong path.
* Template goal lines end with terminal punctuation (. ! ?) — the prescreen GOAL WRAP flag is a wrap heuristic, not a length limit (`skill-corpus-prescreen.sh:109-119`); read the checker before the second fix guess.
* Convention priors from `.rules` must be verified against the codebase before use — rules can be stale.

## Federated recall (hkask-memory)

* A read-only federated source validates only the tables it reads, never producer-owned ones — the exact-match `hmems` admission check coupled sealed sources to storage-schema evolution and rejected every sealed corpus source at the R5 `provenance` migration (2026-10-11).

## Settings and constants

* Kask settings defaults live in `Default` impls only — not in `#[serde(default)]`, `From<Content>` literals, or `mcp_env()` comparison literals.
* The source-shipped DEFAULT_PASSPHRASE ("allostery", `kask/crates/hkask-keystore/src/passphrase.rs`) is a first-run keychain-provisioning convenience, never a server fallback: a managed server that cannot resolve `HKASK_DB_PASSPHRASE` fails closed or degrades — it never opens a SQLCipher DB on the known default. Pinned by `default_memory_passphrase_is_empty_never_the_source_known_default` (security-audit run 1, card 295f2859, commit history 2026-10-24).
* Model-name constants must reference `hkask_inference::model_constants::DEFAULT_*_MODEL`, not re-declare literals across crates.
* MCP server credentials/config are scoped per-server via non-optional allowlists (`credentials`/`config_env` on `BuiltinMcpServer` — `&'static [&'static str]`, no `Option`); declare `&[]` when a server reads none. Allowlists must align with actual env-var reads.
* After `INFERENCE_SOCKET_PATH` is set, call `sync_kask_mcp_runtime_servers` again so servers restart with updated env.
* Passphrase rotation (`run_pending_db_passphrase_rotation`) writes the main keychain slot LAST, after every DB is rotated — a keychain write after a partial rotation leaves DBs unopenable (one `HKASK_DB_PASSPHRASE` for every SQLCipher DB — the full rule lives under MCP server patterns).

## MCP server patterns

* Tool responses are `{"content": <value>}` envelopes — use `unwrap_tool_envelope`, don't re-implement.
* Error classification must be per-variant, not blanket `McpToolError::internal`.
* Missing caller-named resources (id, file, db path) classify `not_found` naming the thing — never `invalid_argument` (that is closed-set validation: name the valid values) or `internal` (that is a server fault). The canonical contract lives on the `McpToolError` constructors (operator ruling 2026-10-05).
* Tool inputs accepting arbitrary JSON must use `AnyJsonValue`, not `serde_json::Value` (schemars renders `Value` as bare `true`, which breaks strict-schema providers).
* Live-mutation probe suites must run with `--test-threads=1` and keep probes self-contained.
* Missing credentials surface as `McpToolError::permission_denied` naming the env var — never `unavailable`, `invalid_argument`, `failed_precondition`, or a silent fallback. Canonical: `ctx.credentials.get("ENV_VAR")` → typed error → `permission_denied` at the tool boundary (reference: `hkask-mcp-corpus/src/helpers.rs` `passphrase_unavailable` — the fail-closed `HKASK_DB_PASSPHRASE` resolution). A missing credential is an authorization failure; silent fallbacks (empty results, in-memory DB, skipped env injection) are broken feedback loops — the operator cannot distinguish "not configured" from "no results" or "provider down."
* The canonical `HKASK_DB_PASSPHRASE` resolution helper is `hkask_mcp_server::server::resolve_db_passphrase(&ctx.credentials)` — a 2-tier chain (ctx.credentials → env → keychain). All MCP servers that consume it use this helper, never inline re-implementations (reference: `hkask-mcp-kata-kanban`).
* There is NO `service=hkask` keychain fallback for API keys — `resolve_credential` reads env vars only (injected by `build_mcp_server_env` from zed's keychain); the legacy `service=hkask` namespace is removed and purged at startup (`hkask-keystore/src/keychain.rs`) — entries written there silently vanish. One `HKASK_DB_PASSPHRASE` for every SQLCipher DB; the internal key `hkask_db_passphrase` lives in `kask://credentials/`. No `*_enabled` settings toggles — the key's presence IS the toggle; a missing key is `permission_denied`, not a silent fallback.
* `write_credential` / `delete_credential` for a credential URL that feeds MCP server env must call `nudge_mcp_servers(cx)` after the keychain write — else the running server keeps the old key until next launch (nudge → `SettingsStore::notify_observers` → `sync_kask_mcp_runtime_servers` → `build_mcp_server_env` → restart).
* Closed-vocabulary MCP string fields reject quoted/padded values unless the server normalizes — the research server's fields all do (since 2026-10-09, `parse_closed_vocab`, `hkask-mcp-research/src/research/types/validation.rs`); other servers' enum fields may still reject them — check which server you are calling before burning retries on a quoting error.

## Dead code patterns

* Trait-with-one-impl is speculative generality — grep for `self.<field>` before merging; if only constructor matches, it's unwired. Generalizes: convention helpers with only test callers are dead code, and folded-service modules with no production callers outside the subtree are dead surface.
* Advertised invariants (doc comments claiming security gates, audit surfaces, migrations) must point to the enforcement line; if none exists, the doc must say "not yet enforced." Validation gates must return `Undetermined`/`Skipped` when the check wasn't performed, not `Ready` with empty findings.
* **Stale comments are active misinformation.** When code behavior changes, every comment describing the old behavior is updated in the same change — agents read comments as ground truth and follow stale comments over user instructions. Grep for comments referencing the changed behavior and update or delete them; a stale comment is worse than no comment. File:line citations — in docs and in pinned claim sets alike — are the same rot: a line-shifting edit to a cited file silently invalidates every citation of those lines — re-verify the citations in the same change, enumerating every file the change touches (diff-driven), not just the files a finding named (live 2026-11-01: the V4 eval-claim pointers survived a sweep that refreshed only the files the finding pattern matched).
* Cargo.toml deps outlive their consumers — when deleting a source file, grep for `use <dep>` in remaining `src/` and `tests/`; zero hits = remove the dep.
* Deletions must clean up what they orphan — no orphan piles, no compatibility states (operator ruling 2026-09-09). Deleting h_mems removes their embeddings and memory_links (`MemoryStore::delete_h_mem` self-cleans; `delete_orphaned_embeddings` is the backstop); deleting a source file sweeps its dep; deleting a capability sweeps its settings knobs and doc sections — all in the same change.
* Capability removals are two-class: live-connection references (client, tools, credential chain, settings row, provider profile, panel group, connection docs, live-tool instructions) go; reference-model citations stay anchored on the published model and are counted in the removal report — zeroing them is over-removal, not cleanliness (operator keep/remove rule). A string sweep under-matches prose describing the removed surface without naming it, so run a concept-word adjudication pass ("cloud", the tool prefix, credential names) over the reworked docs before calling the sweep clean.
* MCP servers are NOT leaf crates — verify dependents before any `pub mod` → `pub(crate) mod` tightening or dead-code verdict. Live production dependents: `kask_bridge` and the kanban panel depend on `hkask-mcp-kata-kanban` (`kask/crates/kask_bridge/Cargo.toml:20`, `crates/kanban_panel/Cargo.toml:19`), and the media panel depends on `hkask-mcp-media` (`crates/media_panel/Cargo.toml:22`). Tightening an item a sibling server or panel imports breaks the build; the harm of the old "zero external dependents" claim was false-dead verdicts from an under-scoped census. Focus dead-code hunts on truly unused items (zero references anywhere, including `tests/`); test seams (`#[doc(hidden)] pub fn from_stores`) are alive even with zero `src/` callers.
* Every removal ends with a full-repo symbol sweep AND a full build before any green claim: `grep -rn` every removed identifier over code AND docs (2026-09-08: a .rs-only sweep left `RegulationCycleEntry` in three doc files), and `cargo check -p zed` for API changes (a scoped two-crate check missed `kanban_panel`'s removed-field construction). `kask/scripts/check-no-new-dead-code-allows.sh` is the backstop; the sweep and the build are the agent's.
* Crate-level `pub` masks dead code — every item is "reachable", so dead-code analysis never fires; a `pub(crate)` conversion pass is the dead-code audit when folding or tightening (live: the services-core fold surfaced 7 dead items, ~30% of the crate; memory's tightening surfaced an 82-line dead cluster).

## Other traps

* Built-in file tools (`write_file`, `edit_file`, `create_directory`) are sandboxed to the project root — writes under `~/Documents/zk-data` (the corpus-mcp/media-mcp/research/zk-reference data dirs) fail with a misleading "parent directory doesn't exist" even when the directory exists. Write via `terminal` heredoc (split long content into `>>` appends) or the owning MCP server's tools. File-tool paths are project-root-relative and UNPREFIXED — a `zed-kask/` prefix is silently accepted and creates a nested `zed-kask/zed-kask/` orphan (`grep`/`list_directory` display paths WITH the prefix — never copy displayed paths verbatim into file-tool calls; observed 2026-10-09, 19-file orphan), and `create_directory` can reject a valid inside-project relative path with "outside the project" — fall back to `terminal` mkdir -p (observed 3× 2026-10-09).
* `LanguageModelInferencePort` honors `model_override` via registry resolution — silently dropping it caused inference calls to use the wrong model.
* `.desktop` files must never declare `text/plain`, `application/x-zerosize`, `x-scheme-handler/zed`, or `Keywords=zed` — enforced at install time by the desktop validation in `kask/scripts/build/install.sh` (the generated file is grepped for exactly these declarations); `check-zed-isolation.sh` guards upstream-file absence, not the declarations.
* LLM-improves-against-LLM-scored-target loops can game the scorer. Three mitigations required: ground in real sources, preserve load-bearing properties, validate against external ground truth.
* `grep -q` exits at the FIRST match — piping a large body into it under `set -o pipefail` SIGPIPEs the writer, and `if !` flips a successful match into a false flag (2026-09-10: ~35% per check on 41KB bodies, `PIPESTATUS: 141 0`). Feed grep from a file or herestring, never `printf | grep -q` on large strings.
* Truncated sweep output silently hides results — a `| head` cap hid five stale doc claims, a byte-capped tool display hid ~14 more, a single-line grep missed a multi-line call (2026-09-18), and a time-only mtime display hid the date: `13:14` read as "written during my batch" was yesterday's build dir (2026-10-22). Count matches first (`grep -c`), consume the full list, page the saved output file, and use full-date `stat` before declaring a time anomaly; never report a sweep as clean from capped output.
* `cp` onto a running executable fails ETXTBSY ("text file busy") — write to a `.new` file then `mv` (atomic rename): the running process keeps its inode, new execs pick up the new binary.
* `pgrep -f` self-matches the invoking shell's own command text — match with a bracket pattern (`pgrep -f "run-conversion-[p]arallel"`) or an exact PID, never the literal command string.
* Never read a file in the same parallel tool batch that edits it — the read races the write and returns pre-edit content (observed 2× 2026-09-10). Sequence reads and edits of the same file across batches.
* In a shared tree, check the staged index (`git diff --cached --stat`) before any `git commit` — the operator's staged work rode into the agent's deletion commit under an unrelated message (2026-09-10, commit 3cf1f7e4a5).
* Re-verify HEAD (`git log --oneline -3`, `git diff --numstat`) before reporting net lines or uncommitted state in the shared tree — an external mid-flight commit makes a bare `git diff` show only the post-commit tail.
* Pathspec-limited commits (`git commit -m "..." -- <files>`) are the default in a shared tree — checking the index is necessary but not sufficient; a bare `git commit` sweeps whatever is staged into your message. A pathspec commit takes the working-tree content of the listed paths — `git add` is a no-op for them, and another stream's unstaged hunks in a shared listed file ride in (live 2026-10-12: a +158-measured commit landed +189, build-broken at its own tree state). Verify the commit numstat against your measured pre-commit diff; on divergence, excise the foreign hunks to a mine-only copy, `git reset --soft HEAD~1`, re-commit with mine-only in the tree, then restore the both-streams file — while the commit is still local.
* Never a working-tree-wide mutation without a pathspec in the shared tree — `git stash` with no pathspec (observed live 2026-10-01, recovered via selective checkout from refs/stash), `git restore .`, `git checkout .`, and `git reset --hard` all sweep every stream's tracked in-flight edits out of the tree at once; only the stash leaves a recovery ref, and `git reset --hard` has no pathspec form at all, so it is never usable here. `cargo fmt --all` is the same class with a milder failure mode (observed live 2026-10-13: it reformats every stream's fmt-dirty in-flight files in place — non-destructive, but the contamination rides their diff unless pathspec-committed); format only the files you measured dirty. If a stash is unavoidable: `git stash push -m '<label>' -- <paths you alone are editing>` and pop or apply only your own labeled entry — the stash stack (refs/stash) is shared and LIFO, so a bare `git stash pop` can apply another stream's entry to the tree.
* A sweep pattern that under-matches the semantic target (wrong plurality, casing, or form) reports false absence — validate the instrument against a known-positive before reading zero as "nothing there" (2026-09-29: a plural-heading grep recorded 8 false reference-model gaps; the bare-glob rule above covers zero-match patterns, this covers valid-but-narrow ones).
* A zero-match instrument's known-positive must validate the same command form, not the same literal — `grep -E 'unwrap_or(0)'` matched `unwrap_or0` (unescaped ERE grouping) while a plain-grep known-positive validated fine, hiding 57 real hits until the escaped re-sweep found them (2026-10-23 audit).
* A `~`-rooted path literal in Rust never expands — `PathBuf::from("~/x")` names a literal `~` directory, so a probe over it structurally reports absence: the P1 `probe_backend` answered `None` on every machine while the HIP build was live at the canonical root (2026-11-04 draft finding; repaired via `hkask_types::agent_paths::resolve_under_data_dir`). Resolve user-rooted paths through the data-dir helpers, and treat a zero-result over a `~`-literal probe as a broken instrument, not absence — the path-literal sibling of the known-positive rules above.
* File metrics (LOC, fn counts, grep hits) mix `#[cfg(test)]` modules with production — split the reading at the first `#[cfg(test)]` marker before diagnosing monolithism or hygiene (live: cycle.rs read as a 3,522-line monolith, 67% test code; a 233-hit unwrap census held 1 production line, itself a comment).
* Consumer maps must be name-visibility censuses over the complete consumer surface, never `use`-import greps — imports are one of three consumption forms (fully-qualified inline paths and method calls on imported types are invisible to import greps; live: `use hkask_memory::` read ~10 consumers, MemoryStore alone has 20+ consumer files). The scan set includes the defining crate's own `src/` (self-consumption — live: hkask-inference's `LOCAL_MEDIA_ROUTER` falsified a "sole consumer" claim) and its `tests/` directory (integration tests are external consumers — live: memory's `tests/federated_source.rs` kept four census-dead items alive). Residual gap: types flowing anonymously through pub signatures are name-invisible — clippy `private_interfaces` adjudicates, not the census (live: 9 of 18 tighten candidates were pub-fn return types).
* A zero-skill-consumer census is triage, never a deletion verdict — panels/widgets (zed-side code), liveness-by-design tools, group-named doc sections, and cross-server code loads all sit outside the skills/templates surface; verify each candidate against those classes before classifying anything dead (2026-10-15/16: the orphan pass and the census verification both closed at zero deletions after full-surface checks found live consumers the census missed).
* jq `(... | select(...)) as $x` runs its body ZERO times when the select matches nothing — a merge loop over entries silently drops every unpatched entry (2026-09-30: 357→17, twice in one recovery). Safe form: `([($patches[] | select(.slug == $e.slug))] | first // null) as $p`, or merge manifests in Rust.
* Verify the invariant, not the shape — `jq -e '.counts'` exits 0 on ANY object; a 5-entry manifest passed it and was installed as canonical (2026-09-30). After every manifest write, assert the count itself: `jq -e '(.entries|length) == 368'`.
* The agent `terminal` runs dash, not bash — `$'\t'` ANSI-C quoting is not a tab there (it split paths at every literal `t` and produced a garbage measurement), and process substitution `<(...)` is a syntax error. Write measurement ladders as saved bash scripts (`kask/scripts/*.sh` under `#!/usr/bin/env bash`), or use `printf '\t'` and temp files (live 2026-10-11: a citation-rot ladder measured 614 rotted from a split path).
* Multi-step `sed -i` edits on one file must re-derive line numbers after every deletion (or apply edits bottom-up), and the s-delimiter must not appear in the pattern or replacement — after `sed -i '7d'` a following `sed -i '8s/…'` targets the line that shifted into 8, and a replacement containing `|` under an `s|…|…|` form silently fails the whole substitution (live twice in one batch, 2026-11-01: a dead-path cite survived its "edit" and an unbound variable was left behind — both caught only by post-edit verification greps; re-read the landed bytes after any scripted multi-edit).
* Scripted per-item edits must cover every definition form the targets take — a `pub` → `pub(crate)` tighten sed written with `pub struct` patterns only silently skipped two `pub enum` candidates (2026-11-01 media census: `JobListParseError`, `CorrectionAlignmentError`; the misses surfaced only when clippy `private_interfaces` bounced them under `-D warnings`). Pin each item's `struct`/`enum`/`fn` form with a definition grep before writing the s-commands — a clean exit reports nothing about forms the patterns never matched.
* Ad-hoc parse/filter/display stages over structured records must key on named fields — `while IFS='|' read -r file form name line` — never positional indices in reads (`awk $N`, `cut -fN`) or sed replacements (`\N`): a positional index wrong for the record's fields fails silently and the wrong result looks clean — an unset awk field reads empty and string-compares false, a cut prints the wrong column, a sed replacement drops a field (three specimens, 2026-11-01/02: the media census's awk `$3` — a field never populated — returned a false-clean "zero candidates" while the count lived in `$2`; the research extraction's sed replacement dropped the name group; the kask_bridge forms display printed names where forms were expected. The named-variable loops consumed correct fields in all three).
* Comparing two instruments' numbers — or recording a defect against one — without pinning what each side actually observes (field, anchor, parse basis, read path) manufactures false findings: the P0 bench's "TTFT candidate" was the SSE flush (TTFB), not the first token (D-F, 2026-11-04); the P2 identity compare watched only `content` while the thinking model emitted into `reasoning_content` — empty-vs-empty reported vacuous identity (F8, 2026-11-05); and the MTP record's D-E "usage misparse" was a tab-collapsed display reading of a correct TSV — the field-aware sweep (`awk -F'\t'`, NF=10, token fields split) refuted the recorded instrument defect 2026-11-06 after it was frozen into the measurement record. Before comparing or condemning, name each instrument's observable and re-read the output bytes with a structure-aware probe (awk field counts, cat -A); refuse comparisons whose observables differ, and never adjudicate an instrument from a lossy rendering of its output.

# Test protocol traps

* A fix that restricts behavior pins the legitimate case it must not break — in the same change (2026-09-29: the O_NOFOLLOW write primitive's inside-root-symlink boundary landed unpinned while the attack was pinned; the D7 short-circuit boundary was pinned only because the lesson was live).

* Cross-seam tests assert category invariants derived from the tree at test time, never hardcoded file-name lists — walk the registry and assert every file of the handled category is covered (2026-09-09: a name-pinned seed test broke on every content rename and silently missed every addition; operator ruling — replaced with the filesystem-derived `collect_seedable_files` walk).
* MCP tool tests must construct the server with the capability under test (embedding store, inference port) — a capability-stripped constructor (`try_new_without_embeddings`, no inference) can only pin degradation, never function (the curator "semantic" tools shipped broken for months because every test used the stripped constructor).
* Degradation tests must assert the degradation is SURFACED (a note/status/mode field naming the reason), never that an empty result equals success — a test asserting `count == 0` on the degraded path enforces the broken behavior as spec.
* `crates/language_model`'s fake: `fake.model(id)` returns a snapshot clone — `update_model` mutates the stored copy. A test that captures the snapshot *before* mutating capabilities leaves the thread on stale defaults; capture `update_model`'s return value (8 failures + 2 latents in the 2026-10-12 merge).
* Recall-path tests must cover the entity_ref JOIN, not just the write: an embedding stored under an entity with no h_mem is an orphan the KNN path silently drops. Test the recall round-trip for every writer variant (curator turns AND non-curator turns).
* When a correctness fix breaks a test, read the test's intent before its assertion — the setup may pin the wrong premise while the purpose is right (2026-09-10: `durable_protection_carries_no_degradation_label` asserted the right behavior over a conflated driver default). Fix the setup, keep the intent.
* The media suite's `educt_render_edl_produces_a_clip_from_a_real_media_file` intermittently fails in full-suite runs while passing in isolation (observed 2026-10-23: red in one of three full runs; isolated and both other full runs green) — re-run it in isolation before blaming your change. The same class reached the widget crate's own layout suite (2026-11-06: `media_widget::layout_tests::video_area_scales_with_window_size` red on CI run 42157758249's first attempt, green on the failed-jobs rerun and locally, dependency graph unchanged) — a real-media layout test reddened once on a loaded runner.
* A load-success gate must assert the observable the failure path changes — the surfaced error or the loaded payload — never a field that exists by construction. An eagerly-built empty holder reads as "loaded": the media widget's `AudioPlayer` is `Some` from construction, so an `is_some()` gate stayed green while the actual load failed on a non-approved-root fixture path, and five false "environment-blocked" facts were derived from the vacuous green before the CI-config review broke the illusion (live 2026-10-25, the S2 audio seek test — the real gate is `widget.error.is_none()` after the async load completes — and a fixture resolves under an approved root only when it sits in the WIDGET crate's own `test_data/`: a consumer crate's `test_data/` is NOT an approved root — see the approved-media-root entry under GPUI traps).
* Plain `cargo check` compiles neither `#[cfg(test)]` code nor `tests/` targets, and a green `cargo test` run does not fail on lints — only the `./script/clippy` gate does. Check-plus-green-tests is not a clean claim: run the gate over the touched kask crates before calling a change clean (live 2026-10-30, twice in one day: `08dc8faf4b` shipped dangling `#[cfg(test)]` builders past a 55-test green run, and `395651cad1` shipped an `== false` under `-D clippy::bool_comparison` — both past a clean `cargo check`).
* Env-setup helper splits + the runner process model (cargo test vs nextest): a test helper variant that skips process-env setup (e.g. a store/driver constructor that omits the env-resolving helper) passes green under `cargo test` — one process, a sibling test's one-shot `set_var` leaks across threads and stably masks the gap in a full-suite run — and fails deterministically or passes *vacuously* under `cargo nextest` (one process per test; an unexercised premise can satisfy the assertions — no runner catches that class, and CI runs the masking runner, so a green CI pass is not evidence the premise was exercised). Any test asserting a successful inference/embedding path must resolve its env through the same helper every sibling uses; refusal-path tests are nextest-only-reliable (observed 2026-10-31: the distillation atomicity tests — one deterministic red, one vacuous green, both stably green under cargo test; fixed in `b8d3c32e1d`).
* Parallel cargo invocations race on shared target-dir artifacts — one process reads rlibs another is writing, surfacing phantom compile errors (an E0277-class trait-bound failure) in one of the concurrent calls that does not reproduce when the scope re-runs alone. The signature: an error in a batch of simultaneous cargo calls against a tree-clean crate, gone on the sequential re-run. Run cargo scopes sequentially in one shell, and re-run the scope alone before diagnosing a compile error seen only under parallel cargo — a defect that survives the sequential re-run is real (live 2026-11-02, batch-11's D83 pins: the race's phantom http_client E0277 vanished sequentially, and that sequential re-run is what separated the genuine http_client serde-derive standalone-scope defect beneath it).

# Concurrent-edit trap

* A build-breaking half-edit left in the tree (e.g. an API change without its call sites) blocks every other agent's validation and is a release blocker, not work-in-progress. If you cannot finish a refactor in one pass, do not leave the tree broken — gate it, branch it, or revert it.
* Inherited committed code must re-pass the FULL gate (`./script/clippy --deny warnings` over the touched scope), not just its own tests — a handoff that calls uncommitted-then-committed changes "validated" on tests alone ships clippy failures (convert.rs charset `and_then`, 2026-10-02).
* Another stream's `git add -A` can overwrite a partial `git apply --cached` mid-turn and sweep finished-but-uncommitted work into its own commit — the shared index and working tree are mutable by every stream (observed 3x 2026-10-28: two staged-index overwrites during a split-file decode-fix commit, then a full commit sweep of gate-verified D96 work that rode in under the sweeping stream's message). Stage split-file work as ONE terminal chain (restore-staged → apply → assert the expected staged numstat → commit), and commit finished work the moment its gates pass — a gate-verified change left sitting through another stream's `git add -A && git commit` loses its attribution.

# Repository fragmentation (absolute prohibition)

* One repository, one working tree, one skills set. Never create a second clone, worktree, or copy of this repository for any purpose — A/B measurement, benchmarking, isolation, or "testing" (operator ruling 2026-10-01). Measurements run as branches in the canonical clone or in-tree; the shared-tree discipline (pathspec commits, index checks) is the isolation mechanism. An agent that perceives a need for a second copy surfaces it and waits — never creates it, and never after being told no.
