`AdherenceDisclosure` is defined at `kask/mcp-servers/hkask-mcp-kata-kanban/src/types.rs:332-347` as a four-field struct — a `sidestepped: bool` flag (`types.rs:335`), a `description: Option<String>` (`types.rs:338`), a `ledger_refs: Vec<String>` (`types.rs:342`), and a `delta_trust_points: i32` (`types.rs:346`) — whose doc comment frames it as what "the completing agent declares about instruction adherence," with "Two forms, both structured" (`types.rs:321-322`). The first valid shape is the no-sidestep disclosure, `sidestepped: false`, which asserts that "no explicit instruction was sidestepped" (`types.rs:323`); it is produced by the `none()` constructor, which sets the flag false, leaves `description` as `None`, `ledger_refs` empty, and `delta_trust_points` at zero (`types.rs:350-358`). This disclosure arrives as the required `adherence` field of `TaskVerifyRequest`, documented as part of the "Binding 6, trust-internalization program" tool contract (`types.rs:312-318`); the service's `task_verify` accepts it as a parameter (`kask/mcp-servers/hkask-mcp-kata-kanban/src/kanban/service_impl/service.rs:842-848`) and attaches it to the stored `Verification` via `with_adherence` (`service.rs:884-885`), where it persists as `Verification.adherence` (`kask/mcp-servers/hkask-mcp-kata-kanban/src/kanban/types/verification.rs:49-53`) and is echoed back to the caller in `TaskVerifyResponse.adherence` (`types.rs:377-385`).

The second valid shape is the sidestep disclosure, `sidestepped: true`, in which "the `description` names what was sidestepped and why; `ledger_refs` cite the trust-ledger event ids; and `delta_trust_points` carries the recorded trust-point change" (`types.rs:324-326`); it is produced by the `sidestepped()` constructor, which takes a description string, the ledger refs, and the trust delta, and sets `sidestepped: true` with `Some(description)` (`types.rs:360-373`). The field docs pin the semantics: `description` holds "what was sidestepped and why" (`types.rs:336`), `ledger_refs` are "the trust-ledger event ids for the sidestepped instructions (citable as evidence h_mems)" (`types.rs:339-341`), and `delta_trust_points` is expected to be negative because "a sidestep never gains trust" (`types.rs:343-344`). The type's doc is explicit that an `AdherenceDisclosure` is "a claim (P — model-judged, cross-checkable against the trust ledger's D-recorded rows where the ledger captured the same instructions)" (`types.rs:328-330`), and the server records either shape without letting it gate completion: pass depends only on non-empty evidence text once the task sits in Review (`service.rs:852-863`). The test suite exercises both shapes — `AdherenceDisclosure::none()` for the clean case (`kask/mcp-servers/hkask-mcp-kata-kanban/src/kanban/service_impl/tests.rs:1834-1839`) and `AdherenceDisclosure::sidestepped("skipped the verification pass to ship faster", …)` for the disclosed case (`tests.rs:1854-1858`).
