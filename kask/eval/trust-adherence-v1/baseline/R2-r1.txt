In `kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs` (cited below as `trust_ledger.rs:NN`), trust-ledger events are persisted as ordinary h_mems in the curator's `MemoryStore` — the module doc states this directly and calls it "Binding 5's substrate," the design point being that because trust events ARE h_mems, `memory_insert`'s evidence gate (`fetch_existing_h_mem`) can cite a trust event's h_mem as evidence for a trust lesson (trust_ledger.rs:7-9, trust_ledger.rs:12-14, trust_ledger.rs:27-29). The module supplies the storage behind the four MCP tools (`trust_ledger_record_instruction`, `trust_ledger_record_outcome`, `trust_ledger_state`, `trust_ledger_steer`) that live on `CuratorServer` (trust_ledger.rs:3-6).

The implementing type is `CuratorTrustLedgerStore`, which wraps an `Arc<MemoryStore>` and a `WebID` (trust_ledger.rs:30-33) and implements the `TrustLedgerStore` trait imported from `hkask_trust` (trust_ledger.rs:21, trust_ledger.rs:99); the h_mem type itself comes from `hkask_storage` (trust_ledger.rs:20). On `append`, the event is converted to an h_mem by `event_to_h_mem` (trust_ledger.rs:100-101), which first serializes the event's fields — text, source, weight as its points value, outcome as one of "kept"/"violated"/"unverified", an RFC 3339 timestamp, and the oracle note — into a JSON value (trust_ledger.rs:41-52), then constructs the row with `HMem::new(TRUST_LEDGER_ENTITY, event.id.as_str(), value, self.webid)`, attaching the store's `WebID` as the fourth argument (trust_ledger.rs:53-58). The persistence itself is a single `store` call on the `MemoryStore`, with any failure surfaced as `TrustError::StoreUnavailable` rather than swallowed (trust_ledger.rs:102-104):

```rust
        self.memory
            .store(h_mem)
            .map_err(|_| TrustError::StoreUnavailable)?;
```

The keying scheme is fixed by the module: the entity is the constant `TRUST_LEDGER_ENTITY` (trust_ledger.rs:24-25), the attribute is the event id, which the doc describes as a UUID (trust_ledger.rs:28, trust_ledger.rs:55), and the value is the JSON carrying the full event (trust_ledger.rs:8-9, trust_ledger.rs:41-52). So each event occupies exactly one h_mem, addressable by its event id inside the shared ledger partition.

Reads and updates go through the same substrate. Both `resolve_outcome` and `window` fetch the partition with `query_deduped_untouched(TRUST_LEDGER_ENTITY)`, mapping query failure to `TrustError::StoreUnavailable` (trust_ledger.rs:114-117, trust_ledger.rs:144-147). `resolve_outcome` locates the target row by matching its attribute against the event id, failing with `TrustError::EventNotFound` when absent (trust_ledger.rs:119-122); it reconstructs the event, applies the resolved outcome and oracle note (trust_ledger.rs:125-127), then persists the change as a delete-then-insert pair — per the in-file comment, HMemStore has no update-in-place, so the old row is removed via `delete_h_mem` and the updated one re-stored (trust_ledger.rs:129-138). `window` filters the fetched rows on the stored `ts` field, parsed back from RFC 3339 and compared against the `since` boundary, then maps survivors through `h_mem_to_event` (trust_ledger.rs:149-160); that reverse mapping decodes the JSON into a `LedgerEvent`, deriving the id from the h_mem attribute and tolerating missing fields with fallbacks such as empty strings and `Utc::now` (trust_ledger.rs:61-96).

Every trust-ledger event is persisted as an h_mem row in the curator's `MemoryStore` under the entity prefix `trust:ledger` (trust_ledger.rs:24-25, trust_ledger.rs:53-58).
