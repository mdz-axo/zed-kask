`AdherenceDisclosure` is defined in the kata-kanban server at `kask/mcp-servers/hkask-mcp-kata-kanban/src/types.rs:332-347` as a four-field struct — `sidestepped: bool` (`types.rs:335`), `description: Option<String>` (`types.rs:338`), `ledger_refs: Vec<String>` (`types.rs:342`), and `delta_trust_points: i32` (`types.rs:346`) — whose doc comment frames it as "what the completing agent declares about instruction adherence," spelling out that there are "Two forms, both structured" (`types.rs:321-322`). It is never a standalone report: it rides in as the required `adherence: AdherenceDisclosure` field of `TaskVerifyRequest` (`types.rs:312-319`, field at `types.rs:318`), documented as "Binding 6, trust-internalization program; the tool contract change the board approved" (`types.rs:315-317`), and is consumed by the service's `task_verify` as a parameter (`kask/mcp-servers/hkask-mcp-kata-kanban/src/kanban/service_impl/service.rs:842-848`). The first valid shape is the no-sidestep disclosure, `sidestepped: false`, which the type doc glosses as "no explicit instruction was sidestepped" (`types.rs:323`). It is produced by the `none()` constructor (`types.rs:349-358`), which sets `sidestepped: false`, leaves `description` as `None`, `ledger_refs` as `Vec::new()`, and `delta_trust_points` at `0` (`types.rs:353-356`); the serde attributes skip the `None` description and the empty refs list on the wire (`types.rs:337`, `types.rs:341`), so this shape carries no payload beyond the false flag and the zero delta.

The second valid shape is the sidestep disclosure, `sidestepped: true`, which the type doc specifies as: "the `description` names what was sidestepped and why; `ledger_refs` cite the trust-ledger event ids; and `delta_trust_points` carries the recorded trust-point change" (`types.rs:324-326`). It is produced by the `sidestepped()` constructor, which takes the description string, the ledger refs, and the trust delta as arguments (`types.rs:360-366`) and sets `sidestepped: true` with `description: Some(description.to_string())` (`types.rs:367-369`). The field docs pin the semantics: `description` holds "what was sidestepped and why" (`types.rs:336`), `ledger_refs` are "the trust-ledger event ids for the sidestepped instructions (citable as evidence h_mems)" (`types.rs:339-340`), and `delta_trust_points` is expected to be negative because "a sidestep never gains trust" (`types.rs:343-344`). The type's doc is explicit that an `AdherenceDisclosure` is "a claim (P — model-judged, cross-checkable against the trust ledger's D-recorded rows where the ledger captured the same instructions)" (`types.rs:328-330`). The server records either shape without letting it gate completion: `task_verify` requires only that the task sit in Review (`service.rs:852-858`) and that the evidence text be non-empty — "Evidence (the user's confirmation text) IS the completion signal. Criteria are informational" (`service.rs:860-863`) — then attaches the disclosure via `Verification::new(...).with_adherence(adherence)` (`service.rs:884-885`), where it persists as `Verification.adherence` (`kask/mcp-servers/hkask-mcp-kata-kanban/src/kanban/types/verification.rs:48-51`) and is echoed back to the caller as `TaskVerifyResponse.adherence` (`types.rs:376-385`). Both shapes are exercised by the test suite: `AdherenceDisclosure::none()` in `task_verify_records_the_adherence_disclosure` (`kask/mcp-servers/hkask-mcp-kata-kanban/src/kanban/service_impl/tests.rs:1834-1839`) and `AdherenceDisclosure::sidestepped("skipped the verification pass to ship faster", vec!["ledger-event-1".to_string()], …)` in the same test (`tests.rs:1854-1858`).
