The trust ledger has no storage machinery of its own — its substrate is the curator's h_mem store. The module header states the design outright: trust events ARE h_mems, persisted by `CuratorTrustLedgerStore`, the `TrustLedgerStore` implementation that "persists trust events as h_mems in the curator's `MemoryStore`" (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:1, kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:7-8). The four MCP tools (`trust_ledger_record_instruction`, `trust_ledger_record_outcome`, `trust_ledger_state`, `trust_ledger_steer`) live on `CuratorServer`; this module only supplies the store they sit on (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:3-6). The store itself wraps an `Arc<MemoryStore>` from `hkask_memory` plus a `WebID`, so an event's durability is exactly an h_mem's durability — the only persistence calls in the module are `store`, `query_deduped_untouched`, and `delete_h_mem` (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:16, kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:19, kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:22, kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:30-33, kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:103, kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:116, kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:133).

Each `LedgerEvent` maps onto one h_mem as a fixed triple: entity, attribute, value. The entity is the shared prefix constant `TRUST_LEDGER_ENTITY` (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:24-25); the attribute is the event id — `event.id.as_str()` is passed as the attribute to `HMem::new`, and the reverse path reads the id back with `LedgerEventId::from_string(&h.attribute)` (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:53-58, kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:64); the value is a JSON object carrying the full event — `text`, `source`, integer weight points, a lowercase `outcome` string, an RFC 3339 `ts`, and the optional `oracle_note` (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:41-52). The struct doc states the same contract: "entity `trust:ledger`, attribute = the event id (a UUID), value = JSON carrying the full event" (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:27-29).

Appending is a single write: `append` converts the event via `event_to_h_mem` and hands it to `MemoryStore::store`, mapping any store failure to `TrustError::StoreUnavailable` (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:100-106):

```rust
        self.memory
            .store(h_mem)
            .map_err(|_| TrustError::StoreUnavailable)?;
```

So a persistence failure surfaces as a typed error, never a silent no-op — behavior the `store_unavailable_surfaces` test pins (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:104, kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:189-213).

Both read paths key off the entity prefix. `resolve_outcome` and `window` each fetch the ledger's h_mems with `query_deduped_untouched(TRUST_LEDGER_ENTITY)`, then work client-side: resolution finds the row whose `attribute` equals the requested event id, while `window` filters by parsing the stored `ts` and keeping events at or after the cutoff (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:114-122, kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:144-160). Resolution is delete-then-insert rather than an in-place update, because the underlying store offers no update path — the comment reads "no update-in-place on HMemStore; delete + insert is the replacement path" (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:129-130): the event is reconstructed with the resolved outcome and oracle note, the old h_mem deleted by id, and the updated event stored as a fresh row (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:124-138). The reverse mapping `h_mem_to_event` is forgiving on read-back, defaulting an unrecognized weight back to `Weight::Explicit` (only 1 → `Implicit` and 2 → `Committed` are recognized), an unrecognized outcome to `Unverified`, and a missing timestamp to now (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:61-96).

The choice of h_mems as the substrate is what closes Binding 5 mechanically: because trust events ARE h_mems, `memory_insert`'s evidence gate (`fetch_existing_h_mem`) can cite a trust event's h_mem as evidence for a trust lesson — the ledger is queryable memory, not a side table (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:12-14). Every trust-ledger event is persisted as an h_mem under the entity prefix `trust:ledger` (kask/mcp-servers/hkask-mcp-curator/src/trust_ledger.rs:25).
