## Findings

### K2-1 (high) — `execute_populate` skips `propagate_taint_for_binding` (FIDES closure break)

**Surface:** code (Layer 5 — Information flow control)
**OWASP LLM 2025:** LLM06 (excessive agency via untrusted data reaching Sinks)
**CWE:** CWE-20 (improper input validation)
**ATLAS:** AML.TA0006 (collection)
**NIST SSDF:** PW.4.1

**Evidence:**

`kask/crates/hkask-templates/src/executor.rs:1285-1299` — `execute_populate`
resolves `input_mapping` via `bind_parameters` and re-inserts the bound values
into `context` with `context.insert(k, v)`, **without** calling
`propagate_taint_for_binding`:

```rust
async fn execute_populate(
    &self,
    step: &BundleManifestStep,
    mut context: HashMap<String, Value>,
) -> Result<HashMap<String, Value>> {
    if let Some(ref mapping) = step.input_mapping {
        let resolved = bind_parameters(mapping, &context);
        if let Value::Object(map) = resolved {
            for (k, v) in map {
                context.insert(k, v);   // ← no propagate_taint_for_binding(v, k)
            }
        }
    }
    ...
}
```

RR-0026 fixed the same closure break at the `resolve_mapping_value` call sites
(`execute_select` L1174, `execute_render` L1335, the loop body L815) but
`execute_populate` uses a *different* resolver (`bind_parameters`) and was
missed. The RR-0026 cargo-test (`propagate_taint_from_inline_jinja_source`)
only tests `propagate_taint_for_binding` directly — it does not assert that
`execute_populate` calls it.

**Impact:** If a prior step produced Source-tainted output (e.g. a `tool_invoke`
against a Source MCP tool returning untrusted external data), and a later
`populate` step binds that value via `{"$ref": "step_N_result.field"}`, the
taint label is lost. A downstream `tool_invoke` against a Sink tool would then
call `check_untrusted_input` and see `Pure` instead of `Source`, bypassing the
FIDES Source→Sink block (Layer 5 defense).

**Remediation:** Add `self.propagate_taint_for_binding(v, k);` before
`context.insert(k, v);` at L1295, matching the pattern at L815/L1174/L1335.
Add a cargo-test that runs `execute_populate` with a Source-tainted context
entry and asserts the bound key is labeled `Source`.

**Proposed regression:** RR-0027 (see below).

### K2-2 (high) — `parse_json_response` and fusion JSON extractor use first-`{`-to-last-`}` (RR-0017 class)

**Surface:** llm-io (Layer 7 — output filtering)
**OWASP LLM 2025:** LLM02 (sensitive information disclosure / output integrity)
**CWE:** CWE-1336 (improper handling of insufficient or excessive data)
**ATLAS:** AML.TA0005 (persistence/ML-model-file tampering via poisoned parsed output)

**Evidence:**

Two call sites use the vulnerable `find('{')` … `rfind('}')` pattern that
RR-0017 explicitly says to avoid:

1. `kask/crates/hkask-templates/src/executor.rs:2331` (`parse_json_response`):
   ```rust
   if let (Some(start), Some(end)) = (trimmed.find('{'), trimmed.rfind('}')) {
       return serde_json::from_str(&trimmed[start..=end]).map_err(...);
   }
   ```

2. `kask/crates/hkask-inference/src/fusion_orchestrator.rs:551`:
   ```rust
   if let (Some(start), Some(end)) = (trimmed.find('{'), trimmed.rfind('}'))
       && let Ok(v) = serde_json::from_str(&trimmed[start..=end])
   { return v; }
   ```

RR-0017 is scoped to `mcp-servers/hkask-mcp-corpus/src/lib.rs` only, so its CI
gate does not catch these two sites. The secure `find_balanced_json_object`
function exists in `kask/mcp-servers/hkask-mcp-corpus/src/json_extract.rs:68`
but is private to that crate — not shared.

**Impact:** An LLM that emits a JSON block in its reasoning preamble (e.g.
echoing an injected instruction) followed by its real answer produces two
top-level objects. The `find('{')`-to-`rfind('}')` slice spans *both* objects
plus the prose between them. `serde_json::from_str` then either fails (no
silent merge, but the step errors) or, if the prose between them happens to be
valid JSON whitespace, silently merges the injected block with the real answer.
The fusion orchestrator is the more sensitive site: it parses panel-model
responses, and a malicious or prompt-injected panel model could poison the
fusion result.

**Remediation:** Extract `find_balanced_json_object` into a shared module
(e.g. `hkask-types` or a new `hkask-json` crate) and use it in both
`parse_json_response` and the fusion orchestrator. Alternatively, duplicate
the brace-balanced scan into both sites. Update RR-0017's `include` field to
cover all three files, or add RR-0028 with the broader scope.

**Proposed regression:** RR-0028 (see below).

### K2-3 (medium) — `llm-guard` exact pin bypassed by per-crate caret spec

**Surface:** supply-chain
**CWE:** CWE-1357 (reliance on untrusted search path / version resolution)

**Evidence:**

- `Cargo.toml:867` (workspace): `llm-guard = "=0.2.0"` — exact-pinned (satisfies RR-0025).
- `kask/crates/hkask-guard/Cargo.toml:15`: `llm-guard = "0.2"` — caret spec, declared directly (not `.workspace = true`).

The crate declares its own `llm-guard = "0.2"` instead of inheriting the
workspace pin via `llm-guard.workspace = true`. RR-0025's detection pattern
(`^llm-guard = "0.2"$` against `../Cargo.toml`) only checks the workspace
root, so it passes while the actual consumer crate floats.

**Impact:** `Cargo.lock` currently locks `llm-guard` to 0.2.0, so this is not
an active vulnerability. But a `cargo update -p llm-guard` would float to the
latest 0.2.x without CI catching it. `llm-guard` is the security-critical
scanner (Layer 1 input filtering, Layer 7 output filtering) — a malicious or
buggy 0.2.x release would silently change the guard's behavior.

**Remediation:** Change `kask/crates/hkask-guard/Cargo.toml:15` to
`llm-guard.workspace = true` so it inherits the workspace's `=0.2.0` pin.
Update RR-0025's `include` to also scan `kask/crates/hkask-guard/Cargo.toml`,
or broaden the pattern to catch `llm-guard = "0.2"` (without `=` prefix) in
any `Cargo.toml`.

**Proposed regression:** RR-0029 (see below).

### K2-4 (low, informational) — `serde_json::to_value(...).unwrap()` in kata-kanban MCP server

**Evidence:** `kask/mcp-servers/hkask-mcp-kata-kanban/src/hkask_mcp_kata_kanban.rs`
has 17 `serde_json::to_value(...).unwrap()` calls in production (non-test)
tool handlers (L93, L123, L174, L233, L284, L317, L352, L391, L426, L465,
L518, L556, L614, L648, L680, L716, L776).

**Impact:** `serde_json::to_value` only errors for non-serializable types
(`f64::NAN`/`Infinity`, or types with custom serializers that fail). The
structs here (`TaskCreateResponse`, `BoardCreateResponse`, etc.) contain only
`String`, `u64`, `bool`, `Vec`, `Option` — none can produce a serialization
error. So these `unwrap()`s cannot panic in practice. This is a code-quality
finding, not a security finding. Per `.rules` ("Avoid using functions that
panic like `unwrap()`"), prefer `.map_err(|e| McpToolError::internal(...))?`
or `expect("TaskCreateResponse is always serializable")` for clarity.

**No regression proposed** — not security-relevant.

### K2-5 (low, informational) — Streaming inference emits leaked text before `scan_output` runs

**Evidence:** `kask/crates/hkask-guard/src/guarded_inference.rs:45-100`
(`GuardedStream::poll_next`). The stream forwards each `text_delta` chunk to
the consumer immediately (L94-96), accumulating a copy. Only when the inner
stream ends (L57) does `scan_output` run on the accumulated text. If a secret
is detected, a redaction chunk is emitted (L67-83), but the leaked text was
already streamed to the UI/consumer.

The code comment at L75-82 explicitly acknowledges this ("we can't un-emit the
leaked text") and labels it the "ART-1 tradeoff". RR-0023 enforces that
`scan_output` is *called* on the stream (the "Output not scanned" pattern is
gone), but does not address the pre-redaction leak.

**Impact:** A secret in the model's streamed output is visible in the UI for
the duration of the stream before the redaction chunk arrives. The stored
assistant message uses the sanitized text (the redaction chunk's
`finish_reason: "redacted"` signals downstream storage to use the sanitized
version), so the leak is transient, not persistent. This is a known tradeoff
between streaming UX and output filtering, documented in the code.

**Remediation (if desired):** Buffer the stream and only emit chunks after a
sliding window has been scanned, or scan each chunk before forwarding (costs
latency). This is a design decision, not a clear bug. Documented here for
completeness; no regression proposed unless the team decides the transient leak
is unacceptable.
