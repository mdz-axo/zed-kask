### K4-1 (critical) — Per-call capability gate compared a caller-supplied value against itself — FIXED

**Surface:** mcp · **CWE-1230** · **OWASP LLM06:2025 (Excessive Agency)** · **Missing layer: 4 (capability gating)**

`McpRuntime::invoke` gated every tool call on
`token.is_valid_for(Tool, tool, Execute)`, and `is_valid_for` is pure equality:

```rust
// kask/crates/hkask-capability/src/token_types.rs:88 (pre-fix)
self.resource == resource && self.resource_id == resource_id && self.action == action
```

All three production mint sites derived `resource_id` from the same `tool` value
they then passed to `invoke`:

| Mint site | `resource_id` argument | Invoked tool |
|---|---|---|
| `crates/zed/src/main.rs:3400` | `tool.to_string()` | `tool` (`:3411`) |
| `kask/crates/kask_bridge/src/inference_ipc_server.rs:763` | `tool.clone()` | `tool` (`:768`) |
| `kask/crates/hkask-templates/src/step_actions.rs:1089` | `tool_name.to_string()` | `tool_name` (`:1096`) |

The predicate was therefore `x == x` — **true unconditionally**. The `||`
right-hand side (`verify_capability_domain`) was unreachable as a denial path.
The only test exercising denial (`invoke_gate.rs:49`, pre-fix) hand-crafted a
mismatched token that no production path can construct. `DIVERGENCE.md` D3
advertised this as "the enforced gate" — the exact security-theater class the
repo `.rules` names ("advertised invariants must point to the enforcement line").

**Remediation applied** (in `kask/` and the D3/D8 seam wiring, per `.rules`):
deleted `DelegationToken`, `panel_default_token`, `capabilities_match`,
`capability_from_server_id`, `CapabilitySpec`, `DelegationResource/Action`,
`verify_capability_domain`, `required_capability_for`,
`ToolInfo::required_capability`, `ToolPortError::CapabilityDenied`,
`TemplateError::CapabilityDenied`, `hkask_types::CapabilityDenied`, and the
`auth.rs`/`resources.rs` modules. `ToolPort::invoke` now takes
`agent: hkask_types::WebID` — an accounting identity, documented as not a
credential. Authority is stated as the three allowlist boundaries that hold a
list the caller does not choose. **Proposed regression: RR-0056 (added,
`enforced`).**

> Operator direction incorporated: capability *separation* is retained and
> documented; per-call capability *gating* is deliberately not reintroduced.

### K4-2 (critical) — `kask/deny.toml` was syntactically invalid; the entire supply-chain policy was inert — FIXED

**Surface:** supply-chain · **CWE-1104** · **OWASP LLM03:2025 (Supply Chain)** · **Missing layer: 6 (runtime/CI monitoring)**

A doubled closing quote at `kask/deny.toml:16` made the file unparseable:

```
$ cargo deny --manifest-path Cargo.toml --config kask/deny.toml check advisories
[ERROR] failed to parse config from '.../kask/deny.toml': invalid character in string: `\n`
$ python3 -c "import tomllib; tomllib.load(open('kask/deny.toml','rb'))"
tomllib.TOMLDecodeError: Unclosed inline table (at line 16, column 325)
```

cargo-deny aborts before reading **any** rule, so no `[advisories]` ignore, no
`[bans]` deny list, no `[licenses]` allowlist, and no `[sources]` restriction was
in force. Compounding it: `grep -rn 'deny' .github/workflows/*.yml` returned
**zero matches** — cargo-deny was never invoked in CI, so an unparseable policy
produced no signal whatsoever. The dead entry on line 16 (`RUSTSEC-2026-0173`,
`proc-macro-error2`, absent from `Cargo.lock`) was itself load-bearing for a
total policy outage.

**Remediation applied:** fixed the quote; removed the confirmed-dead ignore;
added the 8 advisories that appeared once parsing worked (all verified upstream-
transitive via `cargo tree -i`, none kask-introduced, 6 with an upstream patch
pending — recorded as *ignore pending bump*, not accepted risk); set
`[licenses.private] ignore = true` (210 of 222 rejections were the repo's own
GPL crates — a category error drowning 4 genuine third-party rejections, now
explicit exceptions); enumerated `allow-git` (32 hosts; `allow-git = []` against
25 git deps guaranteed 74 errors, i.e. a gate nobody could run). Added a
`cargo-deny` CI job to `.github/workflows/kask-ci.yml`.

Result: `advisories ok, bans ok, licenses ok, sources ok`.
**Proposed regressions: RR-0058, RR-0059.**

### K4-3 (high) — MCP child processes inherit the full parent environment; per-server credential allowlists are bypassed — FIXED

**Surface:** config · **CWE-497 / CWE-668** · **OWASP LLM06:2025** · **Missing layer: 4 (capability gating)** · **STATUS: FIXED (kask path); upstream `context_server` path remains**

`env_clear()` is called on **no** MCP spawn path. Verified:

```
$ grep -rn "env_clear" --include=*.rs crates/context_server/ kask/crates/hkask-mcp/ crates/zed/src/
(no output)
```

Both spawn sites only *add* to an inherited environment:

```rust
// crates/context_server/src/transport/stdio_transport.rs:37
command.envs(binary.env.unwrap_or_default());   // additive; Command inherits parent env
```
```rust
// kask/crates/hkask-mcp/src/runtime.rs:294
let mut cmd = Command::new(&binary);
for (key, value) in &extra_env { cmd.env(key, value); }
```

Meanwhile the parent deliberately loads every API key into its own environment
(`crates/zed/src/main.rs:379`, `dotenvy::from_path`) and injects the SMTP
password (`main.rs:1591`, `std::env::set_var("HKASK_SMTP_PASSWORD", ...)`).

Net effect: all 13 child servers inherit `DEEPINFRA_API_KEY`,
`OPENROUTER_API_KEY`, `ATLASCLOUD_API_KEY`, `HKASK_SMTP_PASSWORD` and every
other `.env`/shell secret regardless of allowlist. `portfolio` — allowlisted
`Some(&[])` / `Some(&[])` — receives all of them. The documented intent at
`mcp_servers.rs:405` ("a server that only needs `DEEPINFRA_API_KEY` won't
receive `HKASK_SMTP_PASSWORD`") holds only for keychain-only secrets, not for
the `.env` deployment `main.rs:344` treats as first-class.

The filter is not useless — `mcp_env_with_credentials` (`settings.rs:1050`)
skips keychain injection when a var is already set, so keychain-only secrets
genuinely are scoped. But the three "blast radius" tests
(`curator_credentials_do_not_include_data_service_keys:690`,
`codegraph_credentials_do_not_include_smtp_password:718`,
`media_credentials_only_include_used_keys:860`) all test
`filter_credentials_for_server` in isolation; none asserts anything about a
spawned child's actual environment, so all pass while children inherit the
secrets they claim to exclude.

**Severity is elevated by K4-1's remediation:** with per-call gating gone, these
allowlists carry more of the authority load, and this is now the widest hole on
that surface.

**Remediation applied** (in `kask/`, per `.rules`): `start_server_with_env` now
calls `cmd.env_clear()` and rebuilds the child environment from
`PASSTHROUGH_ENV_VARS` — 12 non-secret plumbing vars (`PATH`, `HOME`, `XDG_*`,
`TMPDIR`, `RUST_LOG`, `RUST_BACKTRACE`, `LANG`, `LC_ALL`, `TZ`, `SSL_CERT_*`),
each justified in its doc comment — plus the caller's filtered per-server set.

Four tests in `runtime::env_isolation_tests` pin the boundary by inspecting a
**real spawned child's** environment: secrets excluded, allowlisted credentials
still delivered, plumbing retained, and `PASSTHROUGH_ENV_VARS` itself contains no
credential-shaped name (that last one blocks the tempting "fix" of widening the
passthrough list instead of the server's allowlist). **Mutation-verified:**
replacing the clear+passthrough construction with inherit-all makes
`spawned_child_env_excludes_non_allowlisted_secrets` fail with "child inherited
parent secret DEEPINFRA_API_KEY". **RR-0060 enforced.**

**Remaining scope:** the upstream host path
`crates/context_server/src/transport/stdio_transport.rs:37` is untouched — per
`.rules` that is an upstream file, so it needs a D-seam entry + test, or kask
servers routed exclusively through `McpRuntime` (which they already are:
`main.rs:2178`). A context-server-hosted MCP server would still inherit.

### K4-4 (high) — Defense layers 1, 2, 7, 8 are absent: D4 deleted the guard layer

**Surface:** llm-io · **CWE-20 / CWE-200** · **OWASP LLM01:2025 (Prompt Injection), LLM02:2025 (Sensitive Information Disclosure)** · **Missing layers: 1, 2, 7, 8** · **STATUS: OPEN (architectural)**

Seeded hypothesis **confirmed by grep**, not assumed:

```
$ ls kask/crates/ | grep -i guard
(no output)
$ grep -rn "hkask-guard\|hkask_guard" --include=*.toml --include=*.rs crates/ kask/ Cargo.toml
(no output)
$ grep -rn "GuardedInferencePort\|ContentGuard\|Spotlighter\|scan_input\|scan_output\|check_canary\|CanaryToken" --include=*.rs crates/ kask/
(no output)
```

Zero residual references. Consequently:

- **Layer 1 (input filtering)** — absent. No prompt-injection / role-override scan on any inference path.
- **Layer 2 (data/instruction separation)** — absent. `Spotlighter` gone; tool output enters LLM context untransformed (RR-0011 `obsolete`).
- **Layer 7 (output filtering)** — absent. No secret redaction or canary check on model output (RR-0014, RR-0023, RR-0024, RR-0030 all `obsolete`).
- **Layer 8 (deception detection)** — absent. No canary tokens.

This is a deliberate D4 decision (the `RoleOverride` scanner's bare `system:`
substring pattern false-positived on legitimate template rendering). The finding
is **not** "restore hkask-guard" — a scanner that blocks legitimate rendering is
worse than none. The finding is that four layers are absent while the layer
inventory in the prior audit still claims them, and that the compensating
controls are narrower than the deleted ones.

What *does* remain on this boundary, verified: brace-balanced JSON extraction
(`hkask_types::json_extract`, RR-0028 `enforced`), provider-error-body redaction
(RR-0035/0039/0049/0050/0051 `enforced`), ontology-tag validation (RR-0016
`enforced`), SSRF hostname resolution (RR-0048 `enforced`), path containment
(RR-0002/0032/0047 `enforced`).

**Recommendation:** record the absence explicitly (this log + the layer table) so
no future audit re-credits these layers. If Layer 2 is wanted back, prefer
structural delimiting at the *template* level (see K4-6) over substring scanning
— it cannot false-positive on rendering because it does not pattern-match content.

`*_allowlist_matches_actual_reads` tests exist for only 5 of 13 servers

`portfolio:668`). **Unguarded: `codegraph`, `curator`, `research`, `scenarios`,

Confirmed drift, under-grant (read but not allowlisted → silently never arrives):

  `kask/mcp-servers/hkask-mcp-swarm/src/config.rs:252`; verified absent from the
  swarm allowlists (`grep -c` in `mcp_servers.rs` → **0**). Consequence: the

  path**. The existing test `swarm_config_env_includes_all_read_vars:1012` claims

  (`HKASK_SWARM_MEMORY_DB`, `HKASK_SWARM_EMBEDDING_DIM`, `HKASK_A2A_HTTP_ENABLE`).
- **`HKASK_MEDIA_RJOULE_CAP`** — read at
  `kask/mcp-servers/hkask-mcp-media/src/budget.rs:233`, not allowlisted; unset

`OPENROUTER_API_KEY` (`mcp_servers.rs:45`) though the crate's own doc says "no

Dead config with a name mismatch: `companies` reads `HKASK_SERPAPI_KEY`
(`hkask_mcp_companies.rs:317`) while the credential registry declares
`HKASK_SERPAPI_API_KEY` (`inference_providers.rs:213`); it is in neither the
allowlist nor the server's `CredentialRequirement` list, so the error at
`tools/transcript.rs:72` is unreachable.

**Remediation applied:** swarm `credentials` += `HKASK_SWARM_MEMORY_PASSPHRASE`
(a secret, so it belongs in `credentials`, not `config_env`) with a matching
`DATA_SERVICES` descriptor so it is actually sourced from the keychain; swarm
`config_env` += `HKASK_SWARM_MEMORY_DB`, `HKASK_SWARM_EMBEDDING_DIM`,
`HKASK_A2A_HTTP_ENABLE`; media `config_env` += `HKASK_MEDIA_RJOULE_CAP`.

Read-alignment tests added for all 5 previously-unguarded servers, plus targeted
pins for each drift and a generic backstop
(`every_credential_grant_is_secret_shaped_or_documented` — a non-secret name in a
`credentials` list is a classification error, since `config_env` is not treated as
sensitive). Renamed `swarm_credentials_only_include_abw_key` →
`swarm_credentials_exclude_other_servers_secrets`: it asserted a count of 1, which
became false once the passphrase was correctly added — the invariant that matters
is that no *other* server's secret arrives, not the cardinality. **RR-0061
enforced.**

**Deliberately not changed:** codegraph keeps `DEEPINFRA_API_KEY` +
`OPENROUTER_API_KEY`. They have no direct read site, but they *are* reachable via
`resolve_inference_port`'s no-socket fallback (`InferenceConfig::from_env`), so

pinned by a test and documented at the registry entry.

**Deferred:** the `HKASK_SERPAPI_KEY` / `HKASK_SERPAPI_API_KEY` spelling mismatch.
Reconciling it means choosing a canonical spelling across the credential registry,
the server's requirement list, and any operator `.env` files already in use — an
operator-visible rename, not an audit fix.

### K4-6 (medium) — No autoescape on prompt templates; 75% of interpolations are bare

**Surface:** template · **CWE-1336** · **OWASP LLM01:2025** · **Missing layer: 2** · **STATUS: OPEN**

The production `Environment` never configures autoescape
(`kask/crates/hkask-templates/src/template_renderer.rs:337-338`), and the
per-render template is registered under the extensionless synthetic name
`"step"` (`:179`), so minijinja's default callback returns `AutoEscape::None`
for every render. `set_auto_escape_callback` appears nowhere in the repo.

Scale: 404 `.j2` files, 2189 same-line `{{ }}` sites, 537 (24.5%) using
`| tojson`, 1652 bare. **The `tojson` discipline is genuinely working for
cascade step results** — only 13 bare interpolations reference a
`step_N_result`/`prev_step`/`tool_output` name, 8 of them in one skill. The gap
is free-text payloads: `docproc/extract-hmems.j2:94` `{{ text }}`,
`listening/apply-template.j2:194` `{{ chunk }}`,
`diataxis-diagram/present-diagram.j2:12` `{{ file_content }}`,
`registry/selectors/selector.j2:22` `{{ raw_prompt }}`,
`web/search-quick.j2:25` `{{ description }}`, and 8 heal templates
interpolating `{{ error }}` / `{{ error_message }}`. Sharpest:
`curator/template-healer.j2:33` pastes a failed template's own Jinja source into
a prompt whose job is rewriting templates.

Delimiting exists (`<passage>` tags, fenced blocks) but a payload containing the
closing delimiter escapes it, and no sanitizer runs before render
(`template_renderer.rs:185` passes context through verbatim).

Verified clean, worth recording: **zero** `| safe`, `| e`, `| escape`, `| indent`
anywhere; **zero** dynamic `{% include %}` (all literal); path traversal
defended by `safe_template_join` (`:34`) with tests at `:417-447`, `:472-481`
(RR-0002 `enforced`); all 9 `{% raw %}` blocks balanced and documentation-only.

Adjacent, outside RR-0037's `templates/heal` grep scope: `heal/self-heal.j2:22`
advertises `shell.exec` to the model and `:36` instructs running `ls -la`, with a
free-form `"action"` output schema (`:55`) and no "never emit shell commands"
line — unlike its siblings (`command_not_found.j2:43`). RR-0037's
`RunCommand|SetEnv` pattern reports green regardless. Also
`training/trl-sft.j2:37,65` interpolate bare values into Python **string
literals** (`base_model = "{{ base_model }}"`), a quote-escape sink, populated
unescaped at `trl_harness.rs:84,96`.

**Recommendation:** for untrusted free-text, prefer `| tojson` (which quotes and
escapes) or a random-nonce delimiter over bare interpolation; broaden RR-0037's
scope to all of `registry/templates/`; bring `self-heal.j2` in line with its
siblings. **Proposed regression: RR-0062.**

### K4-7 (medium) — Ed25519 private keys pass through unzeroized `String`/`Vec` buffers

**Surface:** code · **CWE-226 / CWE-316** · **OWASP LLM02:2025** · **STATUS: OPEN**

`hkask-keystore` is clean on most axes (see below), but the signing-key path
leaves raw private-key material in heap buffers freed without wiping:

```rust
// kask/crates/hkask-keystore/src/signing.rs:92-93
let key_hex = hex::encode(signing_key.to_bytes());   // raw 32-byte secret scalar -> unzeroized String
keychain.store_by_key(&format!("signing-keys/{publisher}"), &key_hex)
```
```rust
// kask/crates/hkask-keystore/src/signing.rs:103-108  (three more copies)
let bytes = hex::decode(&key_hex).ok()?;   // Vec<u8>, unzeroized
let mut arr = [0u8; 32];                   // stack array, not zeroized
arr.copy_from_slice(&bytes);
Some(SigningKey::from_bytes(&arr))
```

`SigningKey` itself *is* `ZeroizeOnDrop` (`ed25519-dalek` with the `zeroize`
feature, `Cargo.toml:25`) — the crate's doc claim at `signing.rs:28-31` is
accurate — but the four buffers feeding it are not. Same class:
`generate_signing_keypair` (`signing.rs:34-35`) leaves `secret_bytes` unzeroized;
`Keychain::retrieve`/`retrieve_by_key` (`keychain.rs:84`, `:133`) return bare
`String` while the sibling `resolve()` correctly returns `Zeroizing<Vec<u8>>`
(`:208`). `aes-gcm` resolves **without** its `zeroize` feature, so the GHASH
subkey in the long-lived `EncryptionService` (`encryption.rs:45-47`) is not wiped.

Also, missing failure signal (repo `.rules`): `load_signing_key`
(`signing.rs:101-112`) collapses keychain-unavailable, corrupt-hex, and
wrong-length into an unlogged `None`, indistinguishable from "no key configured."

Verified clean and worth recording: **no secret value reaches any log, error
string, or `Debug` impl** — every `tracing` call logs metadata or a key *name*
only (`keychain.rs:218,228,240,257`; `encryption.rs:135`); neither `Keychain` nor
`EncryptionService` derives `Debug`; `#![forbid(unsafe_code)]` present
(`hkask_keystore.rs:1`, `cfg_attr(not(test))`, and zero `unsafe` in production
code); the Argon2/HKDF/passphrase paths are correctly `Zeroizing`-wrapped
end-to-end (`encryption.rs:117-136`, `master_key.rs:56,71`, `keychain.rs:173-186`);
no `let _ =` discards. `subtle` is absent but **correctly so** — there is no
secret-comparison site in the crate at all (signature verification delegates to
`verify_strict`, `signing.rs:68`).

**Recommendation:** wrap the hex string and intermediate buffers in `Zeroizing`;
return `Zeroizing<String>` from `retrieve*`; enable the `aes-gcm` `zeroize`
feature; add a `log::warn!` classifying each `load_signing_key` failure branch.
**Proposed regression: RR-0063.**

### K4-8 (medium) — FIDES taint gate (Layer 5) was structurally present but operationally inert — DELETED

**Surface:** code · **CWE-20** · **OWASP LLM06:2025** · **Missing layer: 5** · **STATUS: RESOLVED BY DELETION**

`with_runtime_policy`, and the policy check does run

`kask/research/seam-audit/security-review.md`.

**Resolution (operator decision): delete, not repair.** Removed

was measured by its plumbing rather than its decisions.

### K4-11 (low, informational) — `HKASK_MCP_{ID}_BIN` accepts any path unvalidated

**Surface:** config · **CWE-426** · **STATUS: accepted (documented threat model)**

`crates/zed/src/main.rs:2816` and `kask/crates/hkask-mcp/src/runtime.rs:100`
